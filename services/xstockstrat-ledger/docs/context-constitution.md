## Rules (`LEDGER-*`) — binding, easy-to-miss conventions

| ID | Rule | Why | Evidence | Example (canonical `path:line`) |
|---|---|---|---|---|
| **LEDGER-1** | **The idempotent-append dedup lookup MUST reuse the transaction's own `client`, never `this.pool.query`.** After `ROLLBACK` it re-queries on the same connection. | The query pool is `DB_POOL_MAX=1`; borrowing a 2nd pooled connection while the txn holds the only one **self-deadlocks** — a hang under load that only reproduces at max=1. | `src/grpc/ledgerServiceImpl.ts#appendEvent` idempotent path (~L99-155) | `src/grpc/ledgerServiceImpl.ts#appendEvent (~L99-155)` |
| **LEDGER-2** | **`StreamEvents` orders subscribe → replay → buffer-flush → go-live** (subscribe to the notifier *before* the history query, buffer live rows while `live=false`, flush deduped-by-sequence, flip `live=true` in one synchronous block). Trimmed NOTIFY rows are resolved in `EventNotifier` before fan-out, in NOTIFY order (serial FIFO, `!draining` fast-path), so `onEvent` only ever sees full rows. The flush stays synchronous. | Replay-first-then-subscribe (the obvious order) silently loses any event inserted during the replay window. | `src/grpc/ledgerServiceImpl.ts#streamEvents (~L246-354)` (comment "Subscribe BEFORE replaying" ~L265); resolve-before-fan-out `src/services/eventNotifier.ts#dispatch (~L165-180)` / `#drain (~L202-272)` | `src/grpc/ledgerServiceImpl.ts#streamEvents (~L246-354)` |
| **LEDGER-3** | **`StreamEvents` clients must resume from their last-processed `sequence` on reconnect** (mechanism: `CLAUDE.md` § Live Streaming Architecture). | A consumer that treats a stream end as terminal (stops) rather than reconnecting-and-replaying the gap loses events. Consumers: xstockstrat-portfolio's **5** permanent subs, all through one resume helper (`services/xstockstrat-portfolio/internal/service/portfolio_service.go#consumeEventStream` → `streamEventsFrom`, `fromSeq = lastSeq+1`) wrapped by `ConsumeOrderFills` (order.filled), `ConsumePositionSyncs` (account.positions.synced), the account-deregistration consumer, `ConsumeBracketUpdates` (order.bracket_updated) and `ConsumeBalanceSyncs` (account.balance.synced); and xstockstrat-analysis's single unfiltered stream (`services/xstockstrat-analysis/app/engine/pnl_pattern_consumer.py#PnLPatternConsumer.run_forever`), which resumes from a DB cursor (`analysis.ledger_stream_cursor`) and drops any `sequence <= cursor` in `process_event`. | producer `src/services/eventNotifier.ts#connect` `onReconnect` loop (~L128-136); consumer `ledgerServiceImpl.ts#streamEvents` `onReconnect` → `call.end()` (~L277-283) | `src/services/eventNotifier.ts#connect` `onReconnect` loop (~L128-136) |
| **LEDGER-4** | **`appendEvent` must NOT set an explicit `sequence` — rely on the column DEFAULT `nextval('ledger.global_sequence')`.** | The old code used a per-stream `event_seq_<md5>` sequence that no migration creates → every write to a fresh stream failed `relation "…" does not exist`. Sequence is globally monotonic. Confirmed `ledgerServiceImpl.ts#insertSql` (~L80-84, 10 insert columns, no `sequence`). | `migrations/001_ledger_events_hypertable.up.sql#global_sequence (~L21)`; PR #639 | `src/grpc/ledgerServiceImpl.ts#insertSql (~L80-84)` |
| **LEDGER-5** | **A long/streaming read MUST NOT hold the `DB_POOL_MAX=1` query pool for its duration** — `ExportEvents` opens a *dedicated* short-lived `pg.Client` (reusing `pool.options.connectionString`/`ssl`) + `pg-cursor`, never `this.pool.query`; `StreamEvents` replays in bounded pool batches, releasing between batches. | Reaching for `this.pool.query` on a new bulk/long read holds the single slot for the whole scan and freezes every `AppendEvent` to `DeadlineExceeded` — the exact scar that produced `pool=1`. Extends the single-listener/query-pool separation contract to reads. | `src/grpc/ledgerServiceImpl.ts#streamExportRows (~L426-455)` (motivation: `exportEvents` docblock ~L373); pool cfg `src/index.ts#new Pool (~L31-37)` | `src/grpc/ledgerServiceImpl.ts#streamExportRows (~L426-455)` |
| **LEDGER-6** | **`ExportEvents` caller scope = the `x-user-id` metadata → `WHERE user_id = $1`; an empty caller matches ZERO rows (never all), and historical `user_id IS NULL` rows are unreachable by design.** The same `callerUserId` helper is also the predicate source for `QueryEvents.owner_only` (`#queryEvents` ~L204-207), so the same empty-caller-matches-zero semantics govern both RPCs; `owner_only` defaults to false (unscoped), so an edge that omits it fails open (CLAUDE.md invariant 5). `GetEvent` (by `event_id`) and `StreamEvents` (stream-key / event-type filters) have no `x-user-id` predicate at all — internal-only by convention (findings). | Treating an empty caller as unscoped, or adding `OR user_id IS NULL` to "include legacy rows," is a cross-user data leak (FR-10). The NULL-never-equals-`''` semantics are load-bearing, not incidental. | caller `src/grpc/ledgerServiceImpl.ts#exportEvents` (`?? ''` via the metadata helper ~L459), predicate `WHERE user_id = $1` (~L404) | `src/grpc/ledgerServiceImpl.ts#exportEvents (~L376-404)` |
| **LEDGER-7** | **`appendEvent` resolves the owning `user_id` dual-channel: `req.userId` wins, else the inbound `x-user-id` metadata, else NULL.** Background producers carry no metadata, so they must set the field explicitly; request-scoped callers ride the header. The `audit.admin_read` producers (root PLAT-15) deliberately set `user_id=owner` while forwarding the admin in `x-user-id` — the field wins. | A new producer that assumes user_id flows only from metadata (drops it in background jobs) or only from the field (drops it for request-scoped calls) writes un-exportable events (silently NULL, invisible to that user's `ExportEvents`). | `src/grpc/ledgerServiceImpl.ts#appendEvent` owner precedence (~L76-78) | `src/grpc/ledgerServiceImpl.ts#appendEvent (~L76-78)` |
| **LEDGER-8** | **The `EventNotifier` LISTEN client runs only single-statement PK reads and session `SET statement_timeout`, bounded by `ledger.stream.resolve_timeout_ms` (server) and 2× (client `query_timeout`). Never a transaction or bulk read.** A resolve TIMEOUT (`errMsg === 'Query read timeout'`) calls `client.end()` (`eventNotifier.ts#drain` ~L258-261), which fires `'end'` → `scheduleReconnect` → `connect()` with `reconnected=true` → `onReconnect` for ALL subscribers, so every live stream does `call.end()`: one slow resolve resyncs the whole fleet (the code comment says so). | A transaction on the LISTEN session holds back NOTIFY delivery, and an unbounded read freezes all fan-out (every live `StreamEvents` subscriber shares this one connection). | `src/services/eventRowResolver.ts#resolveEventRow (~L17-38)` (PK `(event_id, recorded_at)` SELECT, SET-on-change, `query_timeout = 2 * timeoutMs`); wired `src/index.ts#EventNotifier (~L43-46)` | `src/services/eventRowResolver.ts#resolveEventRow (~L17-38)` |
| **LEDGER-9** | **`QueryEvents` pages by an opaque keyset token that is the decimal last `sequence` (a malformed token is code 3 `InvalidArgument`), and every `sequence` compare or encode goes through `toSeq` (pg BIGINT arrives as a string; BigInt, never `Number`).** `StreamEvents` replay is bounded pool batches up to a `max(sequence)` bound captured after subscribe. Delivery contract: a row that commits late with a lower `sequence` than an already-delivered one can be skipped by the live dedupe, the LEDGER-3 resume and the replay bound; batching widens that window to the replay up to the bound. | `nextval` order is not commit order, and `Number(...)` silently loses precision above 2^53 and breaks `"9" < "10"` string compares. The late-commit gap predates 257 (operator sign-off (a)); `pg_snapshot_xmin` is the named follow-up. The per-stream notifier buffer is unbounded while the replay runs (accepted limit). Real-pg proof lives in `src/__tests__/db/queryPagination.db.test.ts` (CI `Ledger DB test (TimescaleDB)`). | `src/grpc/ledgerServiceImpl.ts#toSeq (~L30)`, `#queryEvents (~L166-240)`, `#streamEvents (~L246-354)` | `src/grpc/ledgerServiceImpl.ts#toSeq (~L30)` |
