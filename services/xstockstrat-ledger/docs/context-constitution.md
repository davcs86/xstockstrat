## Rules (`LEDGER-*`) — binding, easy-to-miss conventions

| ID | Rule | Why | Evidence | Example (canonical `path:line`) |
|---|---|---|---|---|
| **LEDGER-1** | **The idempotent-append dedup lookup MUST reuse the transaction's own `client`, never `this.pool.query`.** After `ROLLBACK` it re-queries on the same connection. | The query pool is `DB_POOL_MAX=1`; borrowing a 2nd pooled connection while the txn holds the only one **self-deadlocks** — a hang under load that only reproduces at max=1. | `src/grpc/ledgerServiceImpl.ts#appendEvent` idempotent path (~L99-155) | `src/grpc/ledgerServiceImpl.ts#appendEvent (~L99-155)` |
| **LEDGER-2** | **`StreamEvents` orders subscribe → replay → buffer-flush → go-live** (subscribe to the notifier *before* the history query, buffer live rows while `live=false`, flush deduped-by-sequence, flip `live=true` in one synchronous block). Trimmed NOTIFY rows are resolved in `EventNotifier` before fan-out, in NOTIFY order (serial FIFO, `!draining` fast-path), so `onEvent` only ever sees full rows. The flush stays synchronous. | Replay-first-then-subscribe (the obvious order) silently loses any event inserted during the replay window. | `src/grpc/ledgerServiceImpl.ts#streamEvents (~L246-354)` (comment "Subscribe BEFORE replaying" ~L265); resolve-before-fan-out `src/services/eventNotifier.ts#dispatch (~L139-154)` / `#drain (~L176-246)` | `src/grpc/ledgerServiceImpl.ts#streamEvents (~L246-354)` |

Consumers: xstockstrat-portfolio's **5** permanent subs, all through one resume helper (`services/xstockstrat-portfolio/internal/service/portfolio_service.go#consumeEventStream` → `streamEventsFrom`, `fromSeq = lastSeq+1`) wrapped by `ConsumeOrderFills` (order.filled), `ConsumePositionSyncs` (account.positions.synced), the account-deregistration consumer, `ConsumeBracketUpdates` (order.bracket_updated) and `ConsumeBalanceSyncs` (account.balance.synced); and xstockstrat-analysis's single unfiltered stream (`services/xstockstrat-analysis/app/engine/pnl_pattern_consumer.py#PnLPatternConsumer.run_forever`), which resumes from a DB cursor (`analysis.ledger_stream_cursor`) and drops any `sequence <= cursor` in `process_event`. | producer `src/services/eventNotifier.ts#connect` `onReconnect` loop (~L109-117); consumer `ledgerServiceImpl.ts#streamEvents` `onReconnect` → `call.end()` (~L277-283) | `src/services/eventNotifier.ts#connect` `onReconnect` loop (~L109-117) |

| **LEDGER-9** | **`QueryEvents` pages by an opaque keyset token that is the decimal last `sequence` (a malformed token is code 3 `InvalidArgument`), and every `sequence` compare or encode goes through `toSeq` (pg BIGINT arrives as a string; BigInt, never `Number`).** `StreamEvents` replay is bounded pool batches up to a `max(sequence)` bound captured after subscribe. ## Gotchas & scars

- **RESOLVED (feature 248) — the DB trigger still NOTIFYs a *trimmed* row when the payload exceeds ~7000 chars** (`event_id,event_type,stream_key,sequence,recorded_at` only), but `EventNotifier` now resolves it by PK `(event_id, recorded_at)` on the LISTEN connection before fan-out, so live rows are full. A resolve failure ends the matching streams with 13 (not found) or 14 (error or timeout) and the client replays from its last sequence. Evidence: `migrations/001_…up.sql#notify_event_inserted` trim branch (~L71-80), `src/services/eventNotifier.ts#drain (~L176-246)`, `ledgerServiceImpl.ts#streamEvents` `onGap` (~L285).
- **Immutability is enforced by `deny_mutation` triggers, NOT PostgreSQL rules** (rules aren't supported on hypertables) — the CLAUDE.md wording "PostgreSQL rules" is wrong (findings). Evidence: `migrations/001_…up.sql#deny_mutation (~L47-60)`.
