## Gotchas & scars

- **The Web Push channel gates on severity ONLY; unlike the sibling `FanoutDispatcher` it deliberately does NOT gate on `context.conviction`** ("Never gate on a context key — no producer reliably writes one"). An agent copying fanout's conviction gate into `webPush.dispatch` silently drops pushes for conviction-less alerts. Evidence: `src/fanout/webPush.ts#dispatch` severity gate (~L87-92) vs `fanout.ts#dispatch` conviction gate (~L59-65).
- **VAPID misconfig fails loud ONCE and disables the channel (`vapidConfigured=false`), never throwing per-send.** If all three VAPID vars are present but `VAPID_SUBJECT` isn't `mailto:`/`https:`, the constructor logs ERROR once and disables push — because a malformed subject would otherwise throw on every `sendNotification` and be swallowed to WARN by the per-dispatch catch (a channel that looks enabled but black-holes every push). "Simplifying" the subject regex to a non-empty check re-introduces the silent black-hole. Evidence: `src/fanout/webPush.ts#subjectValid`/`vapidConfigured` (~L66-77).
- **Web Push message TTL and the outbound send timeout are two deliberately-separate constants — never re-conflate them.** `WEBPUSH_TTL_SECONDS = 3600` and `WEBPUSH_SEND_TIMEOUT_MS = 10000` (`src/fanout/webPush.ts#WEBPUSH_TTL_SECONDS` ~L17-18) are passed distinctly to `webpush.sendNotification({ TTL, timeout })` (`#deliver` ~L159-162), pinned by a regression test asserting `opts.TTL === 3600` and a separate real `opts.timeout` (`src/__tests__/webPush.test.ts` "sends a deliberate 1h message TTL" ~L386). The shipped 2026-09-03 defect reused one value for both, passing the 10s HTTP timeout as the TTL — so every push got a 10-second message TTL and any device offline > ~10s silently never received the OS alert. Reusing one constant for both re-opens a whole class of dropped trading alerts with no error.
- **Fan-out ignores `call.write()` backpressure** — `sub.call.write(alert)` drops a subscriber only on a thrown exception; the `false` return (buffer full / slow consumer) is discarded and there is no `drain` handling, so a slow subscriber buffers unbounded server-side. Flagged as an open question in findings. Evidence: `notifyServiceImpl.ts#emitAlert` `sub.call.write(alert)` (~L84).
- **`StreamSubscriber.severities` is typed `number[]` but the runtime fan-out value is a *string* enum** (`stringEnums`) — the only test exercises the numeric path, so CI won't catch a regression if someone numeric-converts one side. Recorded as a latent bug in findings. Evidence: `notifyServiceImpl.ts#StreamSubscriber` (~L14), `#streamAlerts` (~L127), `#matchesSubscriber` (~L280).
