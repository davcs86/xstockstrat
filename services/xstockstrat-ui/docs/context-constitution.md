## Gotchas & scars

- **`@bufbuild/protobuf/wkt` `timestampFromDate(date)` is the canonical Date→Timestamp *constructor*** (`protoTime.ts` has no construct helper, only decode). Request-building code uses it: `useSignalAttribution.ts:2`, `ConfirmFillDialog.tsx:5`, `OrderFilters.tsx:8`, `insights/backfills/page.tsx:4`, `trader/api/ledger/export/route.ts:3` (N=5). Hand-rolling `{ seconds: BigInt(Math.floor(d.getTime()/1000)), nanos: … }` in a request body is verbose, BigInt-mix-prone, and diverges from this convention.
- **Exhaustive `Record<ProtoEnum, …>` render maps are keyed so `tsc` fails on a new enum value** — `roleLabels.ts:6-11` (`ROLE_LABELS: Record<Role,string>`) generalizes the `opportunityShared.tsx` convention ("adding a proto Role value without a label here fails `tsc`"). Two authoritative sites now. Building a role/enum→label with a `switch`+`default` or a partial object renders a new proto enum value as a bare number/blank at runtime instead of failing the build. Evidence: `src/lib/roleLabels.ts:5-10`, `src/lib/opportunityShared.tsx`.
- **PWA support state must resolve SYNCHRONOUSLY; never gate loading on `navigator.serviceWorker.ready`.** `PushToggle` decides support synchronously from feature-detection + `Notification.permission`; reading the existing subscription via `.ready` is fired as best-effort background work, because `.ready` "can hang indefinitely in some headless environments (CI), leaving the control stuck on the spinner." `await`-ing `.ready` before rendering makes the toggle stick on the spinner in CI/headless and flakes the e2e. Evidence: `src/app/accounts/notifications/PushToggle.tsx:31-62`.

- **On any `status >= 400` the BFF dispatch strips `content-encoding`/`grpc-encoding`/`content-length` and forces `content-type: application/json`** — a forwarded downstream `ConnectError` otherwise carries the gRPC response's content-type/encoding and the browser Connect client surfaces a generic "HTTP <status>" instead of the real validation message. Load-bearing for error-message fidelity; don't "simplify" it away. Evidence: `src/lib/bffShared.ts:132-136` (comment `:133-138`).
- **`#901`/`#884` — config-value staleness after save (see `xstockstrat-config`'s CONFIG-6/7/PROTO-5).** `NamespaceEditor`'s Value column and edit-prefill originally read `ConfigKeyMeta.defaultValue` (never updated by `SetConfig`), so every successful save *looked* like a silent no-op until `currentValue` was added (used at `src/app/config-ui/[namespace]/NamespaceEditor.tsx:216`); separately, Save on a `trading_mode='all'` row failed until the page started echoing the row's own registered scope instead of its viewed filter. A future config-metadata read must use `currentValue`, and a future Save must echo the row's own scope, not the page's filter state.
- **`63a3655` — strategy pickers must filter on `live_enabled`, not just `active`.** The Decide "why this fired" picker and the Watchlists per-symbol strategy binding both listed every `active` strategy regardless of `live_enabled`. The real trading loop was independently verified already-correct — this was a read-surface-only gap.
- **`d92960b` — `symbolLocked` is the canonical convention for a page keyed to one fixed symbol.** Signal-detail's `OrderForm` symbol field was fully editable despite the whole page (chart/conviction/edge) being keyed to one symbol; the fix introduced `symbolLocked` (`OrderForm.tsx:76`, `const symbolLocked = Boolean(initialSymbol)`) as the pattern any future single-symbol-context order ticket should reuse rather than reinventing.
