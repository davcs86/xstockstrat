## Open questions (unresolved *why* — needs a maintainer)

- ⚠ **security** — The fundamentals background loop injects `x-access-scope=4` (admin bit) into its own outbound metadata; the admin check is `int(x-access-scope) & 0x04`. Is a background loop self-granting the admin bit the intended trust model? (Cross-cutting with the MCP agent's hardcoded `x-access-scope=7`; tracked in the root findings log.) `app/engine/fundsignal_loop.py:447-448` (`meta.append(("x-access-scope","4"))`, since deleted), admin check `servicer.py:425-437` (`_is_admin`, now `#_has_admin_scope` ~L655) — status: ✓ **RESOLVED** (feature 224): the injection is deleted; the producer now calls ingest/indicators as the reserved `system` identity under the mTLS-SAN-bound `x-internal-caller: analysis-fundsignal` grant (`fundsignal_loop.py` `sys_meta`, no `x-access-scope` in the file)
- Is `LIVE_ENABLED_PREDICATE_SQL` meant to be the single source for the live gate? `entry_backfill.py` re-types the SQL literal instead of importing it, while `live_loop.py` and `strategies.py` import it — deliberate (import cycle through `servicer.py`) or an oversight? — status: **answered 2026-11-04: oversight** — `entry_backfill.py` already imports `app.engine.live_loop` and `app.handlers.servicer` at module top (L22-23) and `app.repositories.strategies` is a leaf that `live_loop` already imports the constant from, so the cycle justification does not hold; the fix itself is still open (report `2026-10-19-analysis-live-gate-sql-duplicated-defect`)
- Can a ledger `order.*` event carry `user_id == "system"` (for example an automated order)? See the `_compose` latent bug above — status: **open**
- `resolve_trading_mode` / `TRADING_MODE` are still sent as the `WatchConfig` subscription scope even though feature 147 removed the axis (`app/config/watcher.py`) — part of the repo-wide disagreement in the root findings log — status: **open**
- **Gross vs. net P&L basis split across the two `realized_pnl` consumers** (2026-09-02): `QueryPnLPatterns` buckets on GROSS `pnl_pattern_samples.realized_pnl` (`app/engine/pnl_pattern_consumer.py#_build_samples` ~L479; sample rows ~L502,523) while `GetAttribution` uses NET (`servicer.py#win = net > 0.0` ~L4457-4458). So the impersonation finding **belongs to feature 132**, not this one; recorded here only so a future reader knows why 133's `x-user-id` propagation did not add a new synthetic-header vector. — status: **deferred to feature 132** **2026-11-04 re-check:** feature 132 is `launched` and `app/engine/live_loop.py` now builds the synthetic owner header via `app/identity.py#owner_metadata` (owner-scoped reads at `live_loop.py` L507/L551/L580); the security question above is therefore live, not deferred. `CLAUDE.md` § Strategy Ownership still says "deferred to feature 132's `resolve_universe`".
