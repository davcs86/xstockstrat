## Rules (`AGENT-*`) — binding, easy-to-miss conventions

| ID | Rule | Why | Evidence | Example (canonical `path:line`) |
|---|---|---|---|---|
| **AGENT-1** | **Every backend RPC opens its own ephemeral `async with grpc.aio.insecure_channel(EP) as channel:` and discards it — no pooled/module-level channel or stub.** | Caching a persistent channel at import diverges from every call site and breaks the connect-per-call assumption the whole client layer follows. | `app/client.py:172` (first `insecure_channel` open; the pattern repeats at ~46 opens across the tool set — the exact line list drifts on every added tool, don't enumerate it) | `app/client.py:172` |
| **AGENT-2** | **Import `gen.*` stubs *inside* each function body (`# noqa: PLC0415`), never at module top.** | The whole `client.py` follows the lazy-import contract (also keeps import-time light); a top-level `from gen.foo.v1 import …` trips the linter and breaks the convention. | first lazy `from gen.*` at `app/client.py:129`; the one top-level exception is `app/auth.py:13` (HTTP-transport path only) | `app/client.py:129` |
| **AGENT-3** | **The *real caller's* derived `x-access-scope`** — computed from the caller's roles by `app/scopes.py` `roles_to_access_scope` — is forwarded so the backend role check *verifies* admin rather than trusting an asserted constant. Since PR #994 it rides on EVERY outbound call via `CallerPropagationMiddleware` (AGENT-4), not just the management write tools; forwarding scope on an open read path is harmless (reads don't gate on it). The management write tools still *derive* the scope through `app/tools.py` `_caller_access_scope` for their own raise-if-missing-claims guard, and the client wrappers still pass an explicit `("x-access-scope", …)` that `_metadata()` de-duplicates against the middleware-bound context. *(Feature 092 removed the old hardcoded `("x-access-scope","7")` `_admin_metadata()` tuple.)* `manage_formula` relies on the indicators backend's author-ownership check, not an admin bit (see AGENT-3b). | Omitting the scope on a write path silently fails the backend role check. | `_caller_access_scope` `app/tools.py:109`; `roles_to_access_scope` `app/scopes.py:41`; `CallerPropagationMiddleware` | `app/tools.py:109` |
| **AGENT-3b** | **A sibling choke point, `_caller_user_id`, sits alongside `_caller_access_scope` — both route through the shared `_require_claims`** — and it must be used (never a plain claims dict-get) anywhere a tool needs the caller's *own* identity rather than their role. It raises rather than falling back to `""` on a missing `user_id`. | Notify's `EmitAlertRequest.target_user_id == ""` is the BROADCAST sentinel (`packages/proto/notify/v1/notify.proto:34`) — a silent empty-string fallback on identity lookup would silently broadcast an alert a caller meant to keep private. Introduced by feature 111 to close a real caller-identity-spoofing gap (see Gotchas & scars). | `app/tools.py:91` (`_require_claims`), `:121-136` (`_caller_user_id`) | `app/tools.py:121-136` |
| **AGENT-4** | **The agent is a platform EDGE and forwards the full propagation trio — `x-user-id` + `x-access-scope` + `x-trace-id` — on EVERY outbound backend gRPC (PR #994, reversing the old "originates, forwards nothing" stance).** A single `CallerPropagationMiddleware` (a `ServerMiddleware` registered in `register_tools`) binds the caller's identity onto `client`'s per-request contextvar (`client.set_caller`/`reset_caller`) for the duration of each `tools/call`, and `client._metadata()` reads that context — so every `client.*` helper forwards the trio with **no per-tool plumbing** (reads included, not just writes). Every header is sourced from the OAuth-verified claims `app/main.py` `_authorized` stamped on the request scope — **never** a caller-supplied parameter, so the feature-111 anti-spoofing guarantees still hold — and a fresh `x-trace-id` is **minted at the edge** when the claims carry none. `_metadata(*extra)` de-duplicates a legacy per-call header against the context, and returns only `extra` when no context is bound (stdio, the pre-token OAuth handshake, direct unit-test calls). PLAT-4 now applies to the agent like any other edge. | Downstream services resolve ownership/audit/trace from these headers; an edge that dropped them (the old stance) left reads unattributable and traces broken at the agent boundary. Sourcing from verified claims — not request params — keeps the forwarding safe. | `CallerPropagationMiddleware` `app/tools.py:156` + `_claims_from_scope_state:144`; `app/client.py` `_metadata:59`/`set_caller:41`/`reset_caller:49` | `app/tools.py:156` (`CallerPropagationMiddleware`) |
| **AGENT-5** | **Tool-layer gRPC error mapping is applied via `_grpc_error_message` + `except AioRpcError → RuntimeError` — a new tool must add it explicitly** (the older tools don't have it; see findings). | Without the wrapper, raw `AioRpcError` leaks to the MCP client. | `_grpc_error_message` def `app/tools.py:189`, applied inside each tool's gRPC-calling body (a new tool must add it explicitly; the exact site list drifts on every tool addition, so it isn't enumerated) | `app/tools.py:189` |
| **AGENT-6** | **`JWT_SECRET` is the HMAC key signing the stateless OAuth `txn` blob (since feature 147, which removed the dedicated `MCP_AGENT_SECRET`)**. It is not sent as an outbound header. Inbound MCP auth requires `claims.aud == AGENT_PUBLIC_URL`. | Rotating the secret affects OAuth transaction integrity; the `aud`/`resource`/`AGENT_PUBLIC_URL` triple must stay aligned. `JWT_SECRET` is now shared between JWT verification and `txn` signing — rotate with that dual role in mind. | `app/oauth_server.py:36` (`JWT_SECRET`), signing `:48-55` | `app/oauth_server.py:36` |
| **AGENT-7** | **`_account_to_dict` PINS every zero-value-omittable scalar (`is_paper`/`is_active`/`halted`) back onto the `MessageToDict` projection so its presence is uniform across every account.** `MessageToDict` follows proto3 JSON semantics: a scalar bool with no field presence is OMITTED at its `false` zero value. Left raw, a `false` field vanishes from some accounts and is present on others, so a tool-consuming agent cannot distinguish `false` from "field absent" (the reported list_accounts confusion). Any NEW zero-value-sensitive scalar added to `BrokerAccount` must be pinned here too — the `test_account_to_dict_covers_every_broker_account_field` F-12 parity guard forces this projection under review whenever a proto field is added. | A silently-absent `false` is read as unknown/missing by the model, not as `false`; uniform presence removes the ambiguity. | `app/client.py` `_account_to_dict` (the `for _bool_field in (...)` pin loop); guard `tests/test_broker_account_client.py::test_account_to_dict_covers_every_broker_account_field` | `app/client.py` (`_account_to_dict`) |

## Gotchas & scars

- **The agent hand-maintains mirrors of ingest's and notify's enum maps** (`_TF_ALIASES`/`_TF_TO_ENUM`/`_FILL_MODE_MAP` mirror ingest; `_SEVERITY_MAP` mirrors notify's `AlertSeverity`). Adding a timeframe/fill-mode/severity upstream without extending these maps breaks the tool. Evidence: `app/client.py:160-165` (`_SEVERITY_MAP`), `:1461-1463` (`_TF_ALIASES`/`_TF_TO_ENUM`/`_FILL_MODE_MAP`).
- **The trading/offline/broker RPCs also hand-encode proto enum *numbers* inline** (distinct from the string-alias maps above): `_OFFLINE_SIDE={"buy":1,"sell":2}` (`app/client.py:1744`), `_OFFLINE_ORDER_TYPE` (`:1745`), `_BROKER_TYPE={"alpaca":1,"ibkr":2}` (`:1750`), and the magic literal `broker_type=3  # OFFLINE` (`:1787`). These must stay in lockstep with the proto enum numbering — a proto enum renumber silently corrupts side/type/broker on every offline/broker RPC. Prefer the generated symbols (as the rest of the file does, e.g. `WATCHLIST_ENTRY_SOURCE_MANUAL` `:407`, `SIZING_MODE_PORTFOLIO` `:628`).
- **`manage_account` `resume` is the ONLY tool with a client-side `0x04` ADMIN gate** (`if not (scope & 0x04): raise PermissionError`, `app/tools.py:1711-1712`) — deliberate defence-in-depth on top of the server-side check. It must stay in lockstep with the `x-access-scope` bit scheme; an agent copying a neighbor tool would omit it.
- **`647988f` (feature 111) — caller-identity spoofing, a second dimension of the AGENT-3/4 risk.** `emit_alert` let any caller address an alert at an arbitrary `target_user_id`, and `manage_formula` let a caller assert an arbitrary `author`/`formula_author_user_id` param — including the literal `"system"`, impersonating indicators' protected `SYSTEM_AUTHOR` sentinel. Fix: both identities are now derived exclusively from verified OAuth claims (`_caller_user_id`, AGENT-3b) — `manage_formula` no longer accepts any caller-supplied author param at all (ownership is unconditionally `_caller_user_id`, `author=user_id` at `app/tools.py:848`), and `emit_alert`'s `target_user_id: str = ""` param was replaced with a required `broadcast: bool` (`app/tools.py:434`, documented `:446-448`) — `broadcast=False` always resolves to the authenticated caller's own id, never an arbitrary target. The lesson: trusting a caller-supplied *identity* parameter is the same class of bug as trusting a caller-supplied *scope* parameter (AGENT-3/4).
