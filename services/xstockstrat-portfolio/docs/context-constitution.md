| **PORTFOLIO-1** | **Broker valuation is authoritative: the shared `unvaluedSymbols`/`applyQuotes` helpers skip any position the broker already valued (`CurrentPrice > 0`) and only fall back to marketdata for un-valued rows, via `markOf` (`mark_price`, else a two-sided mid; a one-sided quote is never averaged)** (feature 229 extracted them from `enrichPositions`; `ListPortfolios`' union batch and `GetPnL` use them too, and `broadcastSnapshot`/`checkRiskLimits` use the same helpers since feature 231). | **PORTFOLIO-2** | **`cost_basis` is stored as *total signed cost* (qty × avg), never per-share** — sells scale `CostBasis` proportionally while holding `AvgEntry`; sync writes `costBasis = qty * avgCost`. | The P&L math `MarketValue − CostBasis` and the winners/losers filter depend on it; storing per-share or recomputing at read time breaks unrealized P&L. | `portfolio_service.go#processOrderFill` (`newCost = existing.CostBasis * (newQty / existing.Qty)` ~L310, block ~L305-315, `UpsertPosition` call ~L355); `internal/repository/portfolio_repo.go#scanPositionRow` (`CostBasis` ~L275), `#UpsertPosition` cost_basis col (~L60-65) | `internal/repository/portfolio_repo.go#scanPositionRow (~L275)` |
| **PORTFOLIO-3** | **All ledger consumers go through one reconnect/resume helper that resumes from `lastSeq+1` in memory and treats `codes.Unavailable` as a benign close. A handler (`eventHandler`) returning an error stops the stream *without* advancing `lastSeq`, so the reconnect redelivers that event; `processOrderFill` returns one for any DB error and emits no ledger event for an unwritten change, the sync and deregistration consumers return their errors through `boundedRetry` (withhold the cursor; park after 5 deterministic attempts, or >= 5 attempts and >= 10 min unclassified; transient errors never park), and only the bracket and balance consumers keep `ackAlways` (best-effort).** | Logging every close at ERROR trips alerting on routine GOAWAYs; resuming from 0 double-counts incremental order fills; acking a fill whose write failed silently corrupts positions (2026-10-02 defect). A permanently failing fill blocks the fill stream (retried every 2s) — by design: surfaced, never skipped. Accepted (feature 256): an outage head-of-line-blocks the sync and deregistration streams until it clears; a park is log-only (`"event parked"` Error) and self-heals on the next boot (`lastSeq` restarts at 0, full replay). (Instance of root PLAT-N3.) | `portfolio_service.go` `consumeEventStream`, `streamEventsFrom` (`if err := handle(ctx, event)`), `ackAlways`, `processOrderFill`, benign-close `isGracefulStreamClose`; `portfolio_fill_errors_test.go` (`TestStreamEventsFrom_HandlerError_DoesNotAdvanceCursor`; a malformed payload is acked and skipped — `TestProcessOrderFill_MalformedPayload_Acked` — so only DB errors withhold the cursor) | `internal/service/portfolio_service.go#consumeEventStream` |

| **PORTFOLIO-9** | **An offline account's `ConfirmOrder` emits `account.positions.synced` ONLY — never `order.filled`.** The two portfolio position consumers are disjoint by event type — `ConsumeOrderFills` (incremental fold) vs `ConsumePositionSyncs`/`GetPnL` (absolute reconcile) — so emitting both would double-count offline positions; `order.filled` is emitted only from the broker fill-poller, which skips offline accounts. | An editable offline confirmation re-runs a non-idempotent incremental fold with no broker snapshot to self-heal, so the offline producer recomputes absolute state and emits the reconciling snapshot instead (feature 157). | **PORTFOLIO-10** | **`account.positions.synced` is an *absolute* snapshot whose consumer runs `DeletePositionsNotInSync` — but the wipe is gated by `shouldReconcileSyncDeletions` (feature 206): an EMPTY positions set purges the account ONLY for an offline recompute (`realized_pnl` present, even `$0`) or account deregistration, NEVER for a broker sync (`realized_pnl` nil).** A broker sync's empty positions list is a non-authoritative/transient broker read; wiping on it deletes a just-order-filled position, which trading's reconciliation poller then flags as a `quantity_discrepancy` and false-halts the account. The offline producer must **still** emit nothing on a failed/uncertain recompute (an empty *offline* snapshot still wipes). | A failed offline recompute emitting empty is indistinguishable from a legitimately-flat offline account and would delete every position, so `ConfirmOrder` returns early without emitting (feature 157).
