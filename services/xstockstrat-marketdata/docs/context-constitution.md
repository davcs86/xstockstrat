| **MARKETDATA-1** | **`Bar.Timeframe` is stored/queried as the canonical DB string (`15m`/`1h`/`1d`), never the Alpaca spelling.** The Alpaca wire spelling (`15Min`/`1Hour`/`1Day`) is used only on the outbound request, then the canonical string is written back onto the Bar. | **MARKETDATA-2** | **Streamed bars carry `1m` and must NOT be persisted** — the stream path deliberately does not `InsertBars`; storage of the continuously-ingested timeframe (`marketdata.stream.bar_ingest_timeframe`, default `1d` since feature 143 narrowed it from `15m,1d`) is owned by `StartBarIngestPoller`/`ingestRecentBars`. ## Gotchas & scars

- **Belt-and-suspenders param defaulting**: Alpaca params (`Adjustment="all"`, `feed="iex"`) are re-defaulted in `adjustmentParam()`/`feedParam()`/`connectAndRead` in addition to `NewClient`, so a Client built without `NewClient` still behaves. Adding a new configured param only in `NewClient` leaves a path that 403s on the free plan. Evidence: `internal/alpaca/client.go:87` (`do`), `feedParam:99`, `adjustmentParam:159`, `stream.go:191`.
- **Pollers/stream run on the long-lived `main` ctx, so their ledger/notify emits carry no propagation headers** (intentional — background work has no inbound request). An agent copying `emitEvent` from a poller into a request-path method drops the headers. Evidence: `cmd/server/main.go:147` (`StartWarmQuotePoller`), `:151` (`StartBarIngestPoller`).
- **SEV-1 scar (root PLAT-8): `WatchConfig` silently subscribed at zero-value scope until 2026-08-07.** `Watcher.environment`/`.tradingMode` fields existed and were sent on every `WatchConfigRequest`, but `NewWatcher` never populated them — so this service (and portfolio) had been silently requesting `UNSPECIFIED` scope since those fields were introduced. Fixed by commit `1413399`'s `resolveEnvironment`/`resolveTradingMode` (MARKETDATA-7). (Feature 147 later dropped the `trading_mode` request half.)
- **`4c91465` — int32-truncation fix in the pool-size env parser.** `strconv.Atoi(v)` + `int32(n)` silently wraps an out-of-range `DB_POOL_MAX` into an arbitrary (possibly negative) `MaxConns` instead of erroring — a CodeQL-caught bug in a connection-pool-budget-sensitive path (root's ~22-connection cluster budget). Fixed via `strconv.ParseInt(v, 10, 32)`. Worth checking any other service that parses an env var straight into an `int32` field the same way. Evidence: `internal/repository/pool.go:26`.
