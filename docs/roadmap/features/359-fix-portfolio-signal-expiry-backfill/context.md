**What**: SEV-3 bug (Track C, Type bug). Portfolio's one-shot `backfill-signal-expiry` APPLY could write a due `signal_id NULL` "untracked mark" next to a live signal and the next prune tick then removed the SIGNAL binding. - Defect-report items worth keeping: the runbook never told operators to quiesce signal ingest during APPLY, and after the fix none is needed (do not add a quiesce step later); once the entry is wrongly removed, nothing restores it until another signal for the symbol re-adds it.
- Why serialize with the parent-row lock rather than fix the add path: `AddSymbols` already holds the parent `watchlists` row lock (`touchWatchlistTx`) and the lock is the documented serialization point for expiry writers; the add path's `mergeSignalExpirySQL` is deliberately UPDATE-only ("untracked stays untracked", @AC-9/@AC-17), so making it upsert would silently CHANGE those rules and edit `watchlist_repo.go`, which feature 354 was editing (R-2). The lock is `FOR NO KEY UPDATE` via a `SELECT`, not the `touchWatchlistTx` UPDATE, because the UPDATE bumps `updated_at`, a user-visible side effect (R-4); the two forms still conflict, so either serializes.
- Why the lock must be its own statement: under READ COMMITTED the INSERT's snapshot is taken at statement start, i.e. before a CTE's lock wait is granted, and EvalPlanQual re-checks only the locked row, not the `NOT EXISTS` subquery — a one-statement `WITH l AS (… FOR NO KEY UPDATE) INSERT …` leaves the race (R-1). Design reasoning from Postgres semantics; it was never demonstrated empirically in this feature (see Deferred follow-ons).
- Why the seed path got the same fix (FR-2): `backfillSeedSQL` has the identical snapshot-then-`ON CONFLICT DO NOTHING` shape and could commit the owner's older, already-expired `valid_until` after a merge that found no row; added to scope as D-4 (appended by the operator as @AC-2).
- Why the production ingest ordering is not a risk (D-5): the agent tool awaits `ingest_signal` and only then runs the watchlist auto-add (`ensure_signal_watchlist` + add; the code logs "signal already ingested" on auto-add failure), and the ingest service has no `AddWatchlistSymbols` caller. Either order is rescued anyway (a mark that lands first is rescued by the later merge); this just closes recon's unverified assumption. (Design cited `tools.py:690`/`:741-747`; the lines have drifted — grep `ensure_signal_watchlist`.)
- Why FR-3's 72h grace is a Go constant, not a config key (F-07, recorded so /sdd-review does not re-flag it): `docs/patterns/config-governance.md:7` scopes the hardcoding ban to env-specific values; this value is the same in every environment and operator-fixed; the one-shot backfill CLI has no config client (`cmd/server/backfill.go:29-61`); product-spec Fix Scope says "No config key changes". `now()` is the per-candidate tx start, so the grace is anchored to each row's own APPLY write (it can differ by seconds across rows of one run).

A future "dedupe the race tests" or "relax strict equality to absent-or-sigID" cleanup would silently disable the guard (R-5).
- Test-design decisions that look arbitrary (D-8/D-9, O-1/O-2): APPLY runs on a pool with NO `lock_timeout` (as `:351-356`), `AddSymbols` on a `testPool` with `lock_timeout=10s`, seed/poll/assert on the 500ms `testPool` — with the 500ms default GREEN would 55P03. The gate has exactly two branches: `addDone` returned (RED on buggy code) or a `wait_event_type='Lock'` waiter whose query is `LIKE 'UPDATE portfolio.watchlists SET updated_at%'` (the `touchWatchlistTx` waiter, chosen so it cannot match the parked INSERT waiter); behaviour assertions run first and `branch == "blocked"` last. A side tx parks an uncommitted `(wlID, symbol)` expiry row: its FK takes `FOR KEY SHARE`, compatible with APPLY's `FOR NO KEY UPDATE`, so the lock still grants and the INSERT parks on the speculative-insert wait. The seed RED needs a prior own signal with a past `valid_until` (`priorSignalAge`, typed `time.Duration`, 0 = none) and REPORT `seedExpired==1`.
- How @AC-1's "after 3 days" Then is tested (impl-spec Step 2): the mark test asserts `until.After(dbNow + 72h)` on the live signal's 30-day `valid_until` without aging anything, and the spec says never to backdate the live signal's row for it. It is not an untested clause; do not "fix" it by backdating.
- @AC-3 test design (D-13): the rewritten tail of `TestBackfill_StrictUntrackedRemoval` reads the DB-written bound `[t0+72h, t1+72h]` (t0/t1 = `dbNow(pool)` around APPLY) so it is not the constant-vs-constant tautology of fails.md:1902-1908; the only clock seam is backdating the row by `72h + 1ms` because the prune uses DB `now()` and D-6 forbids a production clock hook.
