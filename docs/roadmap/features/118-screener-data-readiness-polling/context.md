## Archive Synthesis — 2026-08-19 — /sdd-archiver

**What**: Shipped a UI-only background poll on the Screener page (`/insights/screener`): when a scan returns any `INSUFFICIENT_DATA` row (fundamentals-pending `!gap`, or bars-insufficient `gap`), the page re-issues the **exact same, full** `ScreenSymbols` request on a bounded 60s/5-attempt loop, merges results back by symbol, and shows an honest "Checking… / Stop checking / Gave up" affordance. No proto/servicer/analysis change — the recheck is a plain resend of the unchanged request. Deliberately-scoped middle ground between PR #902's honest-pending-badges fix and a full "notify-when-populated" feature the user declined.

**Why (irrecoverable rationale)**: The decisive choice of *full-scan* recheck (not narrowed still-pending-only) was forced by two findings the shipped code cannot reveal: (1) narrowing breaks universe-relative min-max normalization (`_normalize_universe`) — with one pending symbol left, `lo==hi` collapses every score to a content-free `0.5`; (2) the quota-saving premise for narrowing was *false* once marketdata cache mechanics were traced — `GetFundamentalsMulti`/`GetBars` are read-through caches so resolved symbols are free cache hits, the FMP daily-cap counter only increments on a persisted successful fetch, and a structurally-failing symbol costs the same one live attempt narrow or full. These also justify the cadence being a plain TS constant, not a config key (no shared ops-tunable budget beyond a manual "Run scan again"). The 60s `POLL_INTERVAL_MS` is itself deliberately tuned — aligned to `marketdata.stream.bar_ingest_interval_ms` (60s default) so a bars-insufficient symbol is plausibly caught on the next ingest cycle, and to a same-minute FMP recovery window; the shipped code shows only the bare `60_000` literal, so this constraint is lost with design.md.

**Rejected alternatives**: Narrow recheck to still-pending symbols only — reintroduces the `fix-mcp-screener-correctness` bug class at the client layer AND buys no real quota savings once cache mechanics are traced. New server-side narrower recheck RPC/field — relocates rather than removes the full-universe normalization complexity for a minor compute cost. Config-governed poll cadence — premise (protects a shared FMP budget) doesn't survive the corrected cost analysis. Per-row "dismiss" vs one page-level "stop checking" — over-build for quick-mode scope.

**Scars & gotchas**: Playwright `page.clock` virtualizes only the page's timers, not the real-Node-time resolution of a `page.route` mock — cap-exhaustion tests undercounted attempts until real `page.waitForTimeout(300)` was interleaved between `fastForward()` jumps. The initial-first-poll fires immediately on enable (TanStack no-cached-data mount), counted as attempt 1 of 5, so the real span is ~4 min not the design's ~5. `retry: false` on the poll query is a deliberate third-party-load cap (TanStack default retry=3 would fire up to 4 real FMP/Alpaca calls per tick against a failing symbol, 4x-ing doomed attempts) — shipped with NO inline comment, so it reads as stylistic once specs are gone. git merge rename-detection resurrected a stale pre-renumber `117-screener-data-readiness-polling/` directory during the post-#902 rebase; had to `git rm -r --cached` before completing the merge.

**Permanent deviations**: impl-spec said key the poll-merge `useEffect` on `[poll.data, poll.error]` → shipped keyed on `[poll.dataUpdatedAt, poll.errorUpdatedAt]` because TanStack structural sharing reuses the same `data` reference across byte-identical retries, freezing `pollAttempts` at 1 (already fails.md:823). design said rely on TanStack's default `refetchIntervalInBackground: false` → shipped sets it and `refetchOnWindowFocus/Reconnect/Mount` explicitly `false` (refocus default would bypass the attempt cap).
