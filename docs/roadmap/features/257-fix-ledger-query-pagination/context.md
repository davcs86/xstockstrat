## Archive Synthesis — 2026-11-04 — /sdd-archiver

**What**: Bug fix (SEV-2, debt-radar D-13/D-27/D-46) shipped in PR #1371 and promoted by #1387 (2026-10-31, commit 0cfaa489). Ledger `QueryEvents` now honours `page_token` (opaque keyset = decimal last `sequence`, default page 100, cap 1000, bad token = code 3, `ORDER BY sequence`). Ledger `StreamEvents` replays in `REPLAY_BATCH_SIZE=1000` pool batches up to a `max(sequence)` bound captured after subscribe, with `waitForDrain` backpressure. Portfolio `GetPnL` fails closed (`ErrLedgerUnavailable` -> `UNAVAILABLE`), rejects a repeated page token, pages at 1000 and keeps the largest-magnitude cumulative partial per order. No proto, migration or config change. HEAD anchors: `ledgerServiceImpl.ts:14-16` (constants), `:30` `toSeq`, `:39` `parseSequenceToken`, `:47` `waitForDrain`, `:311-335` replay; `portfolio_service.go:738` `ErrLedgerUnavailable`, `:776` `ledgerPnLPageSize`, `:817` pass-2 compare, `:922` `collectFills`; `portfolio_handler.go:435`. Design-time cites (`:124-176`, `:182-260`, `:718`, `:749-845`, `:829-830`) are all drifted.

**Why (irrecoverable rationale)**:
- Order matters: D-46 was masked by 251's `SourceService: "trading"` filter matching zero rows, so fixing 251 alone would have turned every user's realized P&L into an inflated "success" past 500 platform fills. Hence the hard merge-order row 257 ≤ 251 (251 waits for 257; design.md@1ed63958:111, product-spec.md@1ed63958:125, merge-order.md:81 at HEAD) and the operator's "before or together with" decision (old context.md@1ed63958:14-24, :91-93). Design chose a merge-order row over absorbing 251's one-line fix, to respect the operator's grouping (design.md@1ed63958:196-197).
- Fail closed, not partial: the original loop treated a page error as end-of-data (`slog.Warn` + `break`) and trusted the token contract; a repeated token (old ledger build ignoring the token) is also treated as `UNAVAILABLE` so the rolling-deploy skew fails loudly instead of inflating P&L (design.md@1ed63958:88-92; merge-order.md:105 rolling-deploy note).
- Replay stays on the pool (one statement per batch, connection released between batches) because a dedicated `pg.Client`+`Cursor` per replay adds a backend connection per concurrent replay beyond the 1 pooled + 1 LISTEN budget (F-06), and portfolio holds permanent streams that all replay after a restart (design.md@1ed63958:181-182; stream count: design.md@1ed63958:191 says three at design time; fails.md:3009 and services/xstockstrat-ledger/CLAUDE.md:51 say five). The `max(sequence)` bound exists because an open-ended "loop until short batch" may never terminate under sustained appends. `waitForDrain` exists because batching alone bounds DB connection holding, not server memory: `writeRow` ignored `call.write()`'s return value and never waited for `drain`, so the 200k-event replay in AC-5 would otherwise buffer unboundedly (recon.md@1ed63958:207-208).
- Clamp, never reject, an oversized/non-positive `page_size`, so no caller changes (design.md@1ed63958:200-201). `ORDER BY` moved from `recorded_at` to `sequence` (indexed, matches export and replay); the two differ only for concurrently inserted rows, and GetPnL pass 2 was made order-independent so it does not matter (design.md@1ed63958:45-50, :97-98). Second accepted consequence: `HydrateStops` (first 100, no paging) may pick a different first 100 only when concurrent inserts tie; "accepted and needs no change" (design.md@1ed63958:48-49; recon.md@1ed63958:204-205).
- `GetPnL` page size raised 500 -> 1000 to match the ledger cap: halves the walk at no cost (design.md@1ed63958:193). Walk ceiling formula: `pages = ceil(platform_filled/1000) + ceil(platform_partials/1000)`, `walk_ms ~ pages x per_page_ms`; once `walk_ms` exceeds 50% of the caller deadline, add a user-scoped walk on `idx_events_user_sequence` (design.md@1ed63958:113-117). Availability of GetPnL scales with PLATFORM-wide fill count until then.
- `GetPnL` deliberately does NOT set `ownerOnly` (feature 263's owner predicate): that closed the open risk "263's owner scope drops fills written before migration 003" (old context.md@1ed63958:319-320, :350), so the walk stays platform-wide with an in-process user filter. This is the premise for the availability-scales-with-platform-fill-count fact above, and the user-scoped walk waits on 263's NULL-`user_id` handling.
- Steps 2 (ledger token) and 6 (GetPnL guard) had to ship in ONE integration PR: the repeated-token guard makes `GetPnL` return `UNAVAILABLE` against a ledger that does not yet honour the token (implementation-spec.md@1ed63958:56-57).
- Two build choices carry no code comment at HEAD (`ledgerServiceImpl.ts:208-210` has none): the keyset param is bound as a decimal string (`cursor.toString()`), not a BigInt, "so pg's parameter serialization is not relied on" (implementation-spec.md@1ed63958:162-163); and a missing `MAX(sequence)` bound is never defaulted to `0n` because real pg always returns exactly one row from `COALESCE(MAX(...))`, so a missing row is a fault that takes the catch path (implementation-spec.md@1ed63958:331-332).

**Scars & gotchas**:
- pg returns BIGINT `sequence` as a string (no `setTypeParser`), so every pre-existing `maxSeq` compare in `streamEvents` was lexicographic (`"10" > "9"` false) and every ledger unit mock used a numeric `sequence`, hiding it. Fix: one `toSeq` helper accepting number/string/bigint; tests use `"9"/"10"/"11"` string rows; real-pg token walk in the DB tier. ts-proto decodes int64 as `number` (`packages/proto/buf.gen.yaml` has no `forceLong`; verified in the sdd-spec session, old context.md@1ed63958:321-323; design had flagged it unverified, design.md@1ed63958:43-44, :228-229), so the helper must accept both. Ledger entry already exists (fails.md:3054).
- Operator signed off a weakened delivery contract: "exactly once" holds only for events committed before the walk passes their sequence; a lower sequence committing late is not delivered by that walk. The gap class already existed (live dedupe, LEDGER-3 resume); batching widens its window to the replay length. Written into LEDGER-9. (old context.md@1ed63958:265-269, :286-287)
