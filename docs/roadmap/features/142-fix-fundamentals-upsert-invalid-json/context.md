## Archive Synthesis — 2026-08-31 — /sdd-archiver

**What**: `UpsertFundamentals` in `xstockstrat-marketdata` was failing with SQLSTATE 22P02 on every symbol because the `extra_metrics` bind parameter was passed as `[]byte`, which pgx's `QueryExecModeExec` mode (active under `DB_PGBOUNCER=true`) wire-encodes as `bytea` — independent of any `::jsonb` SQL cast. A first fix (PR #967) added only the `::jsonb` SQL cast, deployed to staging, and the identical error recurred, proving the cast was necessary but not sufficient. PR #969 added the real fix: binding `string(extraJSON)` so pgx sends the `text` OID and the `$14::jsonb` cast becomes a genuine text→jsonb parse. All four steps, including the mandatory live-DB repro, were completed and the fix verified in production (commit `6af00b9d`).
**Why (irrecoverable rationale)**: Under `QueryExecModeExec`, pgx infers each parameter's wire type from the Go argument type without a server round-trip. `[]byte` → `bytea` OID, regardless of any `::jsonb` in the SQL text. Postgres's `bytea::jsonb` cast path goes through bytea's hex-escaped text representation (e.g. `\x7b7d`), which is never valid JSON, producing SQLSTATE 22P02 every time. The root cause was isolated by reading pgx v5 source directly (`conn.go`) after staging confirmed the cast-only fix was insufficient. The `::jsonb` SQL cast still belongs in the query (matches the repo's established Python-service convention) but the Go bind must be `string`, not `[]byte`.
**Rejected alternatives**: Ship `::jsonb` cast without mandatory live-DB repro — lost (unconfirmed hypothesis + no CI gate); Add Postgres CI service container to Go jobs — lost (scope creep for a SEV-3 single-column fix, deferred as future hardening); Repo-wide lint rule enforcing `::jsonb` casts on all jsonb binds — lost (only one jsonb bind in the entire Go codebase; CF-N4).
**Scars & gotchas**: (1) `pgxmock.ExpectExec(...)` defaults to expecting zero arguments unless `.WithArgs(...)` is explicitly called — omitting it causes "expected 0, but got N arguments" at test time. (2) A pgxmock SQL-text pin test alone cannot catch `[]byte`-vs-`string` OID-inference bugs — a custom `pgxmock.Argument` matcher on the argument position is required. (3) The live-DB repro for a pgx `QueryExecModeExec` OID bug does not require Docker or a real PgBouncer process — `DB_PGBOUNCER=true` alone flips the pgx query mode; any accessible real Postgres suffices. (4) Local dev and CI never set `DB_PGBOUNCER=true`, so `QueryExecModeExec` OID-inference bugs are invisible to the automated test suite until staging/production. (5) `MarketDataRepo.pool` is a concrete `*pgxpool.Pool`, so pgxmock injection requires a separate `execer` interface field — no `Exec`-shaped mockable interface existed anywhere in the Go services prior to this feature.
**Permanent deviations**: design.md said `extraJSON` stays `[]byte` → shipped with `string(extraJSON)` bound as `$14` — because `[]byte` → `bytea` OID regardless of the `::jsonb` SQL cast; design pgxmock test was a SQL-text pin asserting the query contains `$14::jsonb` → shipped `TestUpsertFundamentals_CastsExtraMetricsToJSONB` with a custom `isStringArg` matcher on the `extra_metrics` argument position — because the SQL-text-only version would have passed whether the argument was `[]byte` or `string`.
**Cross-feature signal**: All six PgBouncer-pooled Go services (`trading`, `portfolio`, `marketdata`, `indicators`, `ingest`, `analysis`) run with `DB_PGBOUNCER=true` in staging/production. Any of those services binding a `[]byte` argument to a `jsonb`, `json`, or `text` column carries the identical latent OID-inference bug. The safe pattern: always bind `string(bytes)` (not `[]byte`) at jsonb/json/text bind sites in PgBouncer-pooled Go services. As of this feature, `extra_metrics` is the only jsonb bind in the Go codebase — apply this pattern to any future json/jsonb/text column added to those six services.
**Deferred follow-ons**: Adding a Postgres service container to Go CI so that `QueryExecModeExec`-mode jsonb/text OID-inference bugs can be caught without manual repro — explicitly deferred out of scope as a future hardening candidate.
