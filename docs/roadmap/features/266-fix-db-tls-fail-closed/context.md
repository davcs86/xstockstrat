## Archive Synthesis — 2026-11-04 — /sdd-archiver

**What**: SEV-2 bug (debt-radar D-32, defect report `docs/reports/2026-10-21-db-tls-fail-closed-defect.md` (pruned 2026-11-04; git show 9892b610:docs/reports/2026-10-21-db-tls-fail-closed-defect.md)). Ledger, config, identity, notify and the UI config-ui audit route built their `pg.Pool` with `rejectUnauthorized: !!caCert`, so an unset `DATABASE_CA_CERT` silently downgraded to encrypted-but-unverified TLS. Shipped as five byte-identical `dbTls.ts` resolvers (`resolveDbConnection(url, ca)`) called as the first statement of each backend `main()` (UI: in the audit route), a boot `SELECT 1` added to identity and notify, `DATABASE_CA_CERT: ${xstockstrat.CA_CERT}` added to the `xstockstrat-ui` block of both `.do` specs, and one UI vitest platform guard (`services/xstockstrat-ui/src/lib/dbTlsPlatformGuard.test.ts`: AC-5 YAML parse + SHA-256 copy guard + static wiring scan). Merged as #1365 (`bcde6648`), promoted via #1368 (`df521ff5`), launched 2026-10-30. No proto, migration or config key (`DATABASE_CA_CERT` stays a boot env var, F-07).

**Why (irrecoverable rationale)**:
- Triage found the bug was worse than the scan said: `.do/app.yaml` and `.do/app.dev.yaml` bound the CA for the four backends only, so the UI audit pool was *already* unverified in both deployed environments. A code-only fail-closed change would have broken `/config-ui/api/audit` on deploy, which is why the `.do` binding had to ship in the same PR as the route change (context.md 2026-10-21 triage; design item 7).
- Root-cause hypothesis (triage, never contradicted; `product-spec.md@1ed63958:53-56`, old `context.md@1ed63958:19`): the CA was treated as optional hardening, and the pool setup was copy-pasted per service (debt-radar D-20), spreading the fail-open default.
- Throw-on-present, not strip: pg-connection-string lets URL-derived fields override the explicit `ssl` option, so any `ssl*`/`uselibpqcompat` key left in the URL can defeat `{ rejectUnauthorized: true, ca }`. Stripping would silently discard operator intent (`sslrootcert`) while the process reports verification on; throwing surfaces it. No live URL carries such keys (`.do/app.yaml` DATABASE_URL bindings; `docker-compose.yml:27`), so throwing breaks nothing deployed. DO's cluster connection string carries exactly one TLS key, `sslmode=require` (checked 2026-10-30).
- Five copies over a shared package: the UI Dockerfile copies only proto gen plus the UI tree and the backends use `pnpm deploy`, so a workspace package would have touched five Dockerfiles plus `docker-build.md` for a ~20-line function. The per-service `src/mtls.ts` precedent, a SHA-256 hash guard and a scoped DRY exemption were chosen instead.
- The UI returns a generic 500 body instead of `err.message` because, once the pool verifies, a pg hostname-mismatch error would leak the DB host and SANs to the browser; the full error is logged server-side with the trace id (`context.md@1ed63958:101` r1 objection; `design.md@1ed63958:133-134`).
- The canary was re-aimed at the UI route because the deployed backends already verified (CA bound, `!!caCert` true): only the UI route actually changes behaviour. The backend risk is only an empty `${xstockstrat.CA_CERT}` expansion, which would take all four down together, and with config down every other service then blocks at `waitForSnapshot` (`design.md@1ed63958:150-151,200-202`; `context.md@1ed63958:185,286,362`).
- `DATABASE_CA_CERT` is a boot env var, not a `WatchConfig` key (F-07), because it secures the channel config itself reads from; a config key would be circular (`product-spec.md@1ed63958:81-82`; `recon.md@1ed63958:88`).
- Operator sign-off 2026-10-22: identity and notify crash-loop at boot when DB TLS cannot be verified (new boot `SELECT 1`); the deploy smoke check is the detection point. Operator decision 2026-10-21: scope is D-32 only, Track C for all SEV-2, UI failure log carries the inbound trace id.

**Rejected alternatives**:
- Fail closed only when `APPLICATION_ENV` is production/staging (vs on every non-`sslmode=disable` URL) — lost: FR-1 chose every URL (`product-spec.md@1ed63958:32-36`); the debt-radar D-32 finding itself recommended "Fail closed in production" (`context.md@1ed63958:11-12`), so every-URL was a deliberate departure; reason only partly recorded (triage noted no Node service reads `APPLICATION_ENV` except telemetry, `context.md@1ed63958:31-32`).
- Shared `packages/node-db-tls` workspace package — lost: five Dockerfile changes, D-20 out of scope, contradicts the low-rework instruction.
- Strip every `ssl*` URL key — lost: silently discards operator intent while claiming verification (see Why).
- Strip only `sslmode` (round 1) — lost: `ssl=0`/`sslrootcert`/`uselibpqcompat` could override verification.
- Substring `includes('sslmode=disable')` — lost: lets `sslmode=disabled` opt out. Exact match only.
- Keep catch-and-keep-original on an unparseable `DATABASE_URL` — lost: fail-open (old ledger `index.ts:33`, old audit `route.ts:19-21`).
- Fail the Next.js boot instead of the audit route — lost: one admin route would take down all three UI segments; FR-4 asks for route-level failure.
- Validate after `waitForSnapshot` — lost: a missing CA would surface only after the 90 s config wait.
- DB probe before `waitForSnapshot` in ledger/identity/notify so AC-2 could run through `main()` — lost: changes boot order and holds a DB connection through the 90 s wait. Config (no `waitForSnapshot`) got a real `main()` test instead.
- Leave identity/notify without a boot probe — lost: a wrong CA would surface only on the first query.
- AC-5/hash checks in `scripts/workflow-tests/*.test.mjs` — lost: the context-map job has its own paths filter and no YAML parser.
- grep-based `.do` spec check — lost: parse the YAML (existing fails.md lesson).
- One combined mTLS+DB env error — lost: YAGNI/C-18; the reorder is recorded as deliberate (see Deviations).

**Scars & gotchas**:
- Rounds 1 and 2 of the design debate both ended with BLOCKING objections that the proposer had not answered; each was caught by the adversary, not the proposer: r1 (only `sslmode` stripped, hole via `ssl=0`/`sslrootcert`) and r2 (the AC-5 guard never runs on a `.do`-only PR because `ci.yml` had no `.do/**` paths filter; and no test proved each service passes the resolver output to every consumer, so an inline `!!caCert` reintroduced would pass every test).
- Even after two debate rounds and operator approval, the approved rule order had a bypass: rule (b) returned `ssl: false` on `sslmode=disable` *before* scanning for other `ssl*` keys, and a repeated `sslmode` was unseen. pg applies the last duplicate `sslmode` (pg@8.20.0 `connection-parameters.js:59-60`; pg-connection-string@2.12.0 `index.js:39-41,73-78,100-125,145-148`, per /sdd-spec P-03 record, `implementation-spec.md@1ed63958:28-37`; not re-verified since — impl-review could not, `context.md@1ed63958:522-523`), so `?sslmode=disable&sslmode=no-verify` would have connected unverified while the resolver reported `ssl: false` (`implementation-spec.md@1ed63958:40-42`). Found by /sdd-spec's P-03 source read and fixed by throwing on a repeated `sslmode` (`context.md@1ed63958:458-460`). Impl-review separately moved the `ssl*` key scan before the `disable` return as defensive hardening, because the pg source could not be re-read; it added the `?sslmode=disable&ssl=true` throws row (`context.md@1ed63958:510-512`).
- Config boot test must read stderr and stdout together: the fatal error goes to stderr and the winston `db-tls:` canary to stdout, so AC-3's "no `db-tls:`" check covers both streams (`context.md@1ed63958:634-636`).
- Boot-test RED for ledger/identity/notify failed for the wrong reason: the child exited on `mtls: MTLS_CERT, MTLS_KEY and MTLS_CA_CERT must all be set` (`ConfigWatcher` constructor) before reaching any DB check. Asserting stderr contains `DATABASE_CA_CERT` (not just non-zero exit) is what exposed it; fixed by putting the resolver before `new ConfigWatcher`.
- Several tests were green before the fix, so only AC-1/AC-4/AC-7 were genuine REDs: config and Pool-level AC-2 (wrong CA once a CA is set was already rejected by the old `!!caCert` code) and AC-3/AC-8 (`sslmode=disable` was already plaintext). Treat them as PRESERVE guards, not proof of the bug.
- Byte-identity is fragile to formatters: prettier (UI lint-staged) wraps the `parameter "${key}" is not allowed` throw onto three lines; all five copies had to be formatted identically or the hash guard fails.
- Static wiring scan scope: `dbTls.ts` itself must be excluded from both the inline-TLS scan and the `ssl:` allow-list (it is the sanctioned implementation, pinned by the hash); the "exactly two other `ssl:` hits" count only holds with that exclusion (ledger `ledgerServiceImpl.ts:432` `ssl: opts.ssl` at HEAD, `eventRowResolver.ts:42` `ssl: ClientConfig['ssl']`).
