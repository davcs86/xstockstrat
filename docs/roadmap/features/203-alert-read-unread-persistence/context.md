## Archive Synthesis — 2026-10-07 — /sdd-archiver

**What**: Notify alerts got a per-user read/unread inbox: a new `notify.alert_reads (alert_id, user_id, read_at)` table, a `MarkAlertRead` RPC, and `ListAlerts` now returns per-caller `read`/`read_at` plus `unread_count`. "Level / module / body" needed no new fields (they map to `severity`, `category`/`source_service`, `body`). The UI gained `AlertInbox` on `/accounts/notifications` and the `/trader` bell badge shows the server unread count. Launched 2026-09-25 via PR #1177.
**Why (irrecoverable rationale)**: A single global `acknowledged` flag or `read_at` column cannot model "read by A, unread by B" for broadcast alerts (`target_user_id` empty), forcing a join table where a missing row means unread. Read state stays separate from `acknowledged` (FR-1); `AcknowledgeAlert` is not wired in any BFF. The operator's "1+3" answer was read as "extend `notify.alerts` with per-user read state", not a parallel store — never explicitly re-confirmed (an Open Question through spec review).
**Rejected alternatives**: `read_at` on `notify.alerts`; sequential `await` for the two `ListAlerts` queries; a `COUNT(*) FILTER … OVER()` window (repeats per row, marginal at the 50-row cap); `req.limit ?? 50` (0 is the proto3 default) and `|| 50`; a secondary index on `alert_reads(user_id)` (the PK covers MarkAlertRead and the LEFT JOIN; recon's "PK + index" was overridden); a separate repository layer; an optimistic local badge increment on each streamed alert (dropped at build time); a UI "unread only" toggle (never built; AC-4 is unit-tested only).
**Scars & gotchas**: A non-correlated `WHERE EXISTS` in the bulk `INSERT … SELECT unnest($1)` gates the whole batch (a mixed `[valid, phantom]` batch inserts everything); caught at impl-spec review, shipped as a per-row `JOIN notify.alerts` (`notifyServiceImpl.ts:176-179`). The design justified it by FK violations, but the table has NO FK — the JOIN only prevents inert orphan rows, and a malformed non-UUID id still throws at `$1::uuid[]` (code 13). proto3 zero-default / JS falsy on `limit` (`> 0 ? : 50`, `:194`). `Promise.all` of the two `ListAlerts` queries serializes at notify's pool max 1. Host-native codegen fallback (Docker Hub 429) produced `analysis.pb.go` whitespace drift, reverted (fails.md:2378). The mock backend replays 3 stream alerts, making a "server count + stream increments" assertion non-deterministic (5 vs 2), and its `markAlertRead` is a no-op, so the AC-1 UI check relies on a `page.route()` intercept. On launch every historical alert is unread for every user (no backfill; `notify.alert.retention_days` is documented but unimplemented). `refetch` sets `loading=true`, so the list flashes to skeletons on each mark-read.
**Permanent deviations**: Design said the badge increments optimistically per streamed alert → shipped a pure server-count badge fetched ONCE on mount with no refresh trigger (the Deviation Log's "next refetch" names none), so marking read in the inbox or a new streamed alert leaves it stale, and `hasHighSeverity` (`AlertStream.tsx:52`) still comes from session-local streamed alerts. "Mark all read" is bounded to the loaded 50 rows (`AlertInbox.tsx:28,55`), so the server `unreadCount` can stay above 0. Design said `ListAlerts` owner "replaces the current body-based `req.userId`" as a security tightening → shipped header-first with body fallback (`notifyServiceImpl.ts:192`): with no identity `$1::text IS NULL` matches every row and `unread_count` equals the total — real only because the BFF `forward()` always injects `x-user-id` (`bffShared.ts:40,72`); direct gRPC callers are unscoped; unlogged. `markAlertRead` has NO `target_user_id` ownership check (`:164-186`): any caller can mark any existing alert id read for themselves (inert, but probes id existence). The design's "unread_only filter toggle" e2e was not built; the promised phantom-id test only regex-asserts the SQL against a mock pool, and AC-2's per-user isolation is checked only via `rowToAlert` with `read_at: null`, yet AC-1..AC-5 were promoted to a durable suite that asserts more than the tests prove.
**Cross-feature signal**: Feature 165 owns migration 002 and the push RPCs; 203 took 003. `registerPushSubscription` already used the `x-user-id` header while `AcknowledgeAlertRequest` keeps a legacy body `user_id` (C-03 inconsistency left untouched). The inbox reuses `notifyClient` through the `/trader/api` BFF under the sanctioned cross-segment exception; `AlertStream`'s `limit:1` fetch is a count-only trick.
**Deferred follow-ons**: Unread-only UI filter; broadcast entitlement and per-category unread counts; an agent MCP tool for alerts; `AcknowledgeAlert` still unwired in the UI; `ListAlerts` ignores `categories` and `page_token`; a pool-max-1 latency assertion. Doc drift to fix: `services/xstockstrat-notify/CLAUDE.md:26` omits `MarkAlertRead` (and the feature-165 push RPCs) and `alert_reads`; `services/xstockstrat-ui/CLAUDE.md` "PWA & Push" never mentions `AlertInbox` and its notify dependency row still says "alert stream" (ledger traps fails.md:597, 308). A live-DB apply was deferred to CI/deploy.
**Runtime-invariant recommendations (→ /context-constitution)**: Notify: `ListAlerts`/`MarkAlertRead` take the owner from `x-user-id` metadata and fall back to the body `userId`; only `MarkAlertRead` rejects when both are missing; a null identity makes `ListAlerts` unscoped (or fix the code and delete the fallback). `notify.alert_reads` has no FK to `notify.alerts`; the per-row JOIN is the only orphan guard, with no cascade on alert deletion.
