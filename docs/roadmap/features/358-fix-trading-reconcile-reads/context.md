## Archive Synthesis — 2026-11-18 — /sdd-archiver

**What**: `reconcileTick` (xstockstrat-trading) read one 500-row portfolio `ListPositions` page per broker account and dropped `next_page_token`, so an account with more than 500 positions read every later symbol as platform qty 0 and could be halted (`HALT_SOURCE_RECONCILIATION`) on a position the platform actually held. The fix is a trading-local helper `listAccountPlatformPositions` (`trading.go:2085-2131`) that drains the cursor into a complete symbol→qty map or returns `nil` plus a page-indexed `%w` error, which routes into the unchanged `ppErr` skip (WARN, `continue`, no candidate, no halt, not systemic). Each skip increments one new OTel counter `trading.reconciliation.position_check_skipped{outcome=rpc_error|deadline|cursor_invalid}` (`reconcilePositionSkipCause`, `trading.go:2134`). No proto, migration, config key, env var or portfolio change. Shipped via feature PR #1578 (`eca0c1ee`, commit date 2026-11-17, squash into main-dev) and promoted to main by PR #1580 (feature.md Status History; launched 2026-11-18). Zero behavioural deviations from design; the execute-phase deviations were process-only (see Scars).

**Why (irrecoverable rationale)**:
- Fail-safe direction: a false finding halts the account (blocks `PlaceOrder`/`ReplaceOrder`), so every incomplete read skips the account for the tick and never halts. The operator decision recorded at sdd-review (context.md sdd-review block: "skip-the-account-for-the-tick on any incomplete read, never a halt; follow docs/roadmap/ledger/fails.md:3311 (fail closed, reject a repeated token, test against a fake that ignores the token)") is the root of D-2. The debate state blocks and D-2 evidence relay it as the shorthand "skip, never halt" (relayed wording, not the sdd-review text).
- Per-page `context.WithTimeout(broker.timeout_ms)` plus `x-user-id` on every page, not one shared deadline (R-1/D-3): a shared deadline would make a large account hit the deadline every tick and never be checked, with nobody noticing. Accepted cost (D-3 as written: "acceptable because the loop-termination rules exist and missed ticks are dropped", i.e. a slow drain does not pile up ticks): tick time grows by up to ceil(n/500) x `broker.timeout_ms` per large account because the account loop is sequential. The timeout is passed in as a parameter from the single per-tick `brokerCallTimeout` read (D-19); reading config per page was rejected (R-14) because a config change mid-drain would alter D-3 partway and force the direct-helper tests to stand up a config watcher.
- Guard order inside each page is load-bearing (D-9/R-7): the token guards (empty page with a token, repeated `next_page_token`) run BEFORE the symbol merge, and the duplicate-symbol guard runs last. In the round-2 order (merge first) the duplicate-symbol check fired first on any ignore-token fake and shadowed the repeated-token check, so deleting the seen-token check left every test green (the fails.md:3312 trap; blocking objection O-6). The shipped code (`trading.go:2111-2123`) has the D-9 order; `TestListAccountPlatformPositions_358_Guards` pins each guard's exact page-indexed text so deleting any one turns a row red.
- Duplicate symbol across (or within) pages fails closed (D-5/R-3) rather than sum or last-write-wins: portfolio's `UNIQUE(user_id, symbol, trading_mode, account_id)` (portfolio migrations/003:10) means only a broken cursor can produce a duplicate. The text is `page %d: duplicate symbol %q` without "across pages" (D-13) because the same check also catches an in-page duplicate.
- The seen-token set is defense-in-depth against portfolio's monotonic keyset cursor (D-4/O-5), not a response to a real cycle scenario; the code comment is capped at 2 lines and the full rationale belonged in the PR description.
- Helper returns `map[string]float64`, not a slice (D-16/R-11, round-4 O-17): the slice's only consumer was the map the D-5 dedup already built; `trading.go:2244-2247` (the rebuild) was deleted.
- `ppErr` skips stay out of `systemicCount` (D-7/R-6): counting them would change REDUCE_ONLY escalation semantics (@AC-45 @feature-294); a portfolio outage skipping every account therefore never escalates, as before. `resolveUnknownIntents` (old `:2292`) is also skipped on that `continue`; kept deliberately, out of scope.
- Positive control (D-10/O-1/O-7): without a test where page-2 SYM501 has qty 5 vs broker 10 and asserts `mismatch_found` payload `expected == 5`, `broker_reported == 10` (read only from the existing `recordingLedgerClient`, D-14/R-9), a drain that fetches page 2 and then discards it would pass AC-1..AC-3 while silently disabling position reconciliation (breaking @AC-2 @feature-206). RED for that test is `expected == 0` on the old code.
- AC-1's RED rationale (O-8): on the old code the pre-seeded `acc-1:pos:SYM501` candidate does NOT survive; tick 1 raises it to 2 >= 1+graceTicks and `recordReconciliationCandidate` deletes it and returns true (`trading.go:2041-2044` at design time), so RED comes from the finding and halt assertions, and "key absent" only discriminates a correct compare from a skip when paired with "no finding". recon.md had said AC-2 "may pass vacuously before the fix"; the debate (O-4) corrected that: AC-2 fails RED naturally (SYM501 missing, diverges, halts), and the `p2`-was-requested assertion is a GREEN-side guard.
- Deadline-ordering test (D-11/D-18/R-8/R-12): "page-1 ctx still live" cannot tell per-page deadlines from a shared one (R-8); the test asserts page 2's entry-captured `Deadline()` is strictly after page 1's, with page 1 doing `time.Sleep(5ms)` and NEVER observing ctx (a ctx-selecting page-1 fake could turn an overrun into a page-1 error, so page 2 would never log and the assertion would flake). The 50 ms `broker.timeout_ms` also governs the broker calls (`brokerCallTimeout`), so broker fakes must never sleep or block (O-13). A fake clock was rejected (R-10): `context.WithTimeout` does not use `s.clock`, so it would be a new speculative seam.
- Per-iteration identity (D-17/D-20, O-15): the paging fake serves by token alone, so a drain that dropped `x-user-id`, `AccountId` or `TradingMode` on page 2+ would pass every AC and then silently skip or compare the wrong set in production. The fake logs `{PageToken, x-user-id, AccountId, TradingMode, Deadline}` at call entry; `takeLog()` copies and resets per tick (D-15) so a single tick that loops one extra time is detectable (a cumulative 4-call total cannot). Expected values are a named `reconcile358Owner` placed in `brokerPoolEntry.userID` and the LITERAL `commonv1.TradingMode_TRADING_MODE_PAPER`; every 358 broker fake sets `isPaper: true` because the field's zero value drives LIVE (`trading.go:2227-2230` at design time) and re-deriving the expected mode from `IsPaper()` would mirror the mapping under test (R-13). Round 5's own proposal wrongly assumed fixtures were "paper unless a live toggle exists" (O-18).
- The counter (D-21..D-24). It was NOT in the product spec or the triage; it was added at the design gate (see governance). It is separate from `trading.escalation.systemic` (R-15: that instrument is unlabelled and means REDUCE_ONLY escalation; reuse would break @AC-45 and R-6/D-7). Unlabelled single counter rejected (R-16): it could not distinguish a persistent deadline skip on a large account from a transport outage or a cursor bug. Skip cause is classified with `errors.Is` on package sentinels (`errEmptyPageWithToken`, `errRepeatedPageToken`, `errDuplicateSymbol`) wrapped with `%w`, never by message text (D-22/R-17), so the D-12/D-13 strings stay byte-identical.
- Outcome mapping: `deadline` when `errors.Is(err, context.DeadlineExceeded) || status.Code(err) == codes.DeadlineExceeded` (both forms: a ctx-blocking fake returns plain `context.DeadlineExceeded`, for which `status.Code` is `Unknown`; the AC-2 deadline fake returns that plain form; the lesson itself is at fails.md:4047). The three guards share one `cursor_invalid` label because the WARN already names the guard (O-22: C-18, five labels was more than needed; per-guard labels were NOT kept and the register's O-22 "otherwise record why" alternative was not taken). `context.Canceled` maps to `rpc_error`, so every deploy/shutdown produces a burst of `rpc_error` skips for the remaining accounts; this is counted, accepted and documented (`reconciliation.md:102`), with no sixth label (O-24); a future alert needs a rate or for-duration window.
- Counter tests (D-23): each calls `installMetricReader(t)` as its FIRST statement and none uses `t.Parallel`; a missed install makes the zero-count guards (AC-1 and positive control assert total 0) pass without testing anything. The instrument is also in `minInstruments` and `driveAllInstruments` (`telemetry_allowlist_test.go`), so the label-allowlist loops cover it.
- No `packages/otel/produced-signals.tsv` row, alert or dashboard (D-24): `scripts/check-otel-produced-signals.py` only requires rows for series an alert or dashboard queries. "Alertable" means an operator can build one; any later alert PR must bring the row in the same PR.
