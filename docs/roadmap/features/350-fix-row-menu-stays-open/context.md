# Context: fix-row-menu-stays-open  (archived 2026-11-18)

**Feature**: ./feature.md
**Status**: launched — archived by /sdd-archiver; verbose specs pruned (recoverable via git history).

## Archive Synthesis — 2026-11-18 — /sdd-archiver

**What**: A row-actions menu item that asks for confirmation no longer keeps its menu open and modal behind and after the dialog. `RowActionsMenu` stops calling `preventDefault` on confirm items so Radix closes the menu through its normal closing state; the dialog's `onCloseAutoFocus` returns focus to the row's trigger, or to the enclosing `<main>` when the trigger is gone or disabled; a one-shot flag stops the closing menu from stealing focus back on the keyboard path. The orders table (Cancel) and the strategies list (Deactivate) deleted their own menu-plus-dialog copies and adopted `RowActionsMenu`. Every table's actions cell had to keep its component identity across the confirm flow, so authorized apps, config templates and strategies got stable cells. UI only (`xstockstrat-ui`); no proto, migration, config key or env var. The integration PR is #1565 (squash commit `ccbe424c`, confirmed with `git log`); promotion PR #1573 launched it on 2026-11-17 (`feature.md` status row; main commit `dd41417d`). Playwright specs only, because Vitest is node-only and has no component harness.

**Why (irrecoverable rationale)**:
- The defect report's hypothesis ("`preventDefault` stops the menu's close from racing the dialog opening") was right about the mechanism and wrong about the premise. Recon measured the no-`preventDefault` variant in headless Chromium, 4/4 on mouse and keyboard: the dialog opened every time. No test, ledger entry or doc records an observed race. The call came in with `a2107eed` (feature 124, PR #919, 2026-08-09) for the orders table and the strategies list, and was copied into the shared `RowActionsMenu` by `c2077ddd` (PR #977, 2026-08-17), whose comment promised a "defer to the next tick" that the code never did. This is the lesson already at fails.md:4025; not re-written.
- Sites classified at recon: `RowActionsMenu`, `OrdersTable` and strategies Deactivate are the same defect. The opportunities source-filter `preventDefault` (`DropdownMenuCheckboxItem`, multi-select) is a deliberate keep-open and stays; it is pinned by `@AC-7`, which is a guard and not a RED test. The report listed `strategies/page.tsx:306` and `opportunities/page.tsx:257` as "not yet checked"; that resolved to one defect and one deliberate non-defect. Other menu-to-dialog items (`accountShared.tsx` "Edit keys", `config-ui/users`, `NamespaceEditor`) already open dialogs without `preventDefault` and were the in-repo proof that "menu closes, dialog opens" works.
- Focus fallback is the page's `<main>` (D-6), with `tabIndex={-1}` and `outline-none` on the four segment `<main>` elements (trader and insights `AppShell`, `accounts/layout.tsx`, `config-ui/layout.tsx`) and `preventScroll` on the fallback focus (D-12). Rejected: leave focus on `<body>` (a keyboard user restarts from the top), next row's trigger (may not exist, per-table code). Measured: after a removed row, focus moved to `<main>` and the next Tab landed on the first control in the page content.
- The one-shot skip flag on the menu's `onCloseAutoFocus` (D-3/D-12) is set only by a confirm choice and consumed once, so a dialog dismissed inside the menu's roughly 100 to 140 ms close animation still gets its own dialog focus return. All hooks sit above the `actions.length === 0` return. Measured on the keyboard path: 0 focus events with the guard, 2 without (`focusout` Cancel toward the trigger, then `focusin` Cancel). The mouse path keeps one `focusout`/`focusin` pair toward the closing menu's content (Radix item pointer-leave); focus never lands outside the dialog on either path. D-3's original claim (round 1) was narrowed by D-16 in round 3; design.md (§ Chosen Approach item 3) and the shipped code agree (keyboard path only; the mouse-path pair is a known, unguarded residue reported in the PR), so this is not a design-vs-shipped divergence.
- Stable actions cell is required, not optional (D-5, O-1): TanStack `flexRender` renders a function `cell` as a component type, so any `columns` rebuild remounts every cell, dropping the open dialog and the focus target. Per site (D-10): orders `columns` deps become `[cancelOrder]`; strategies' deps cannot be stabilised because `scoreById` changes on every scores poll, so the cell is a module-level component with its own `useIsAdmin`/`useRouter`/`useManageStrategy`; authorized apps replaces page-level `revoking` with a module-level cell and a local busy flag; config templates was unstable today (D-10 corrects D-5's "check and pin"), fixed with `useCallback`s over a destructured `mutate`, and `errorMessage` moved to module scope. Signal sources (no confirm action) and accounts (not a `DataTable`, already stable) were left alone. `AccountManagementPanel` has no importer, so trigger names and Tab target are unambiguous on `/trader/accounts` (O-11). The columns-remount trap is recorded in two places only (D-14): a two-line comment on `DataTable`'s `columns` prop and the DataTable row of `docs/patterns/ui-ux-governance.md` (verified present); no new constitution ID.
- The trigger is reached by a ref passed to `DropdownMenuTrigger` (Radix composes it with its own); it reaches the DOM `<button>` only because the App Router runs Next's vendored React 19 (ref-as-prop) while the repo is on React 18.3.1 (D-11, O-7). A change there fails the `@AC-3` tests loudly. `composeEventHandlers` skips Radix's own `onCloseAutoFocus` once ours calls `preventDefault`; the dialog focus rule and the one-shot menu flag both rely on that (`react-dropdown-menu`/`react-dialog` `dist/index.mjs`, found at spec time).
- The D-3 guard test (D-17) was redesigned at round 3 after petition P-1. The proposer's first form (count `focusin` on the trigger) can never fail in Chromium: the dialog's trapped focus scope refocuses its own control during the blur, so the trigger never receives a focus event (O-12; recon addendum). Final form: one keyboard-driven test on `/trader/accounts` ("Alpaca Paper" then Remove) with a recorder armed on the first `focusin` inside the dialog that logs every later `focusin`/`focusout`, a positive signal (a `focusScope.autoFocusOnUnmount` listener on the menu element) that Radix's close-focus actually ran, then an empty-log assertion plus "Cancel still focused". Evidence is a mutation run with the guard branch deleted. Measured at Step 2: production build 5 failed, then 5 passed restored; dev server 5 failed (4 on the empty-log assertion, 1 on a `page.goto` compile timeout), restored 4 passed and 1 failed on the same first-navigation compile timeout.
- Deliberate non-goal (product-spec Out of Scope): confirmation dialogs opened from a plain button rather than a menu item (watchlist delete, formula delete, backfill cancel) are not part of this defect and were not touched; a future reader should not read them as missed sites. Also out of scope: any global animation or reduced-motion change in CSS or in the Playwright configuration.
- No per-item test-id prop was added to `RowActionsMenu` (C-18, impl-spec Step 5 instruction 5): the orders `edit-<id>`/`cancel-<id>`/`cancel-<id>-confirm`/`cancel-<id>-dismiss` test ids were deleted and their specs moved to role locators (they were referenced only by `e2e/trader/orders.spec.ts`); only the trigger's `actions-<id>` ids were kept.

**Rejected alternatives**:
- R-1 open the dialog only after the menu finishes closing (from the menu's `onCloseAutoFocus`): about 100 ms with nothing on screen, focus visits the trigger first, and extra state is needed because that callback also fires on Escape and outside click.
- R-2 `modal={false}` on the row menus: does not close the menu; changes outside-click and assistive-technology hiding for every row menu (FR-5).
- R-3 keep `preventDefault` and drive the menu's `open` by hand: re-implements Radix's close at every site; orders has no per-row component to hold the state.
- R-4 share only a hook and keep the orders/strategies markup: orders has one table-level dialog and no per-row trigger ref, so it needs a near-copy of `RowActionsMenu` (C-18) and keeps a dialog with no title or description (C-17).
- R-5 fallback focus on `<body>` (fails FR-3); R-6 fallback to the next row's trigger (may not exist, per-table code); R-7 a `contentRef` branch in the unmount cleanup (the dialog's `onCloseAutoFocus` fires on every unmount, so connected-or-`<main>` covers it; O-7 corrected two wrong premises about refs and about that firing).
- R-8 fix the remount once in `DataTable` by calling function cells directly instead of `flexRender`: breaks any cell that uses hooks, including the strategies cell. R-9 a context provider or DataTable `meta` prop for strategies: new plumbing, the module-level cell is smaller. R-10 find the trigger by overriding its `id`, via `aria-labelledby`, or a wrapping `<span>`: breaks labelling, the content is unmounted once closed, extra DOM in every cell.
- R-11 remove the mouse-path focus pair with an item `onPointerLeave` override keyed on the one-shot flag: intercepts Radix pointer/roving handling on every confirm item for a pair a pointer user cannot perceive (C-18). R-12 settle the guard test with `requestAnimationFrame` then `setTimeout(0)`: scheduler-dependent, and an empty log cannot tell "guard worked" from "close-focus never ran". R-13 assert only "no `focusout` toward the trigger": misses a bounce anywhere else.
- Not measured and so never rejected on evidence: a deferred-dialog variant and `modal={false}` were reasoned out, not probed (recon § Browser measurements, "Not measured").

**Scars & gotchas**:
- Test-design traps found by running: an open dialog marks the menu `aria-hidden`, so role queries skip it and "menu not shown" passes on unfixed code. The settle helper therefore counts `[role="menu"]` with a CSS locator (hidden elements included), asserts `body > [aria-hidden="true"]` count 0 and the computed `pointer-events` of `body` (O-3, D-7). `getByRole('main')` count is not a valid assistive-technology check. A permanent `body > [aria-hidden="true"]` node on any page would be a deviation, not a reason to loosen the helper (spec open thread; none was found).
- "Menu closed after Confirm" is a guard, not RED, on strategies and authorized apps (the remount removes the stuck menu); the RED assertion there is trigger focus (O-4, D-13, Step 8). The `@AC-9` rows are RED only after the mechanism lands and before the stable cell (D-18); Step 4's RED on the Steps 1-2 tree (2 failed at `expectFocusOnMarkedTrigger`) is the evidence D-10 is needed. `@AC-10` on today's code is RED only because the menu never closes. Waits on focus assertions first wait for a rendered outcome (error text, status, item gone), because `waitForResponse` then `toBeFocused` can pass before the remount (O-13).
- Orders flake found only after the PR opened (full local e2e on the production build: 692 passed, 1 flaky): the orders confirm test failed at the marker check once and reproduced 10 times in 34 runs under 4 workers. Cause: the orders table remounts once at page load when the selected account resolves and `useOrders` is re-keyed, so a marker set before that is lost. Fix was test-only: `markTrigger` became `openMarkedRowMenu` (tag and open through the tagged node, so a remount in between fails loudly) and the orders block waits for the first account-scoped `ListOrders`. An intermediate attempt (mark after the menu was open) was wrong because an open menu hides the trigger from role lookups, and was replaced before any push. After: orders feature-350 tests 100/100 under load, all feature-350 tests x4 (76 runs) passed. This refines the "mark before the flow" advice at fails.md:4030; see the new fails entry.
