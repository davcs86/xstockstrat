## Archive Synthesis — 2026-11-18 — /sdd-archiver

**What**: The symbol-page indicator panes (trader → Overview) now draw a long-lookback indicator across the whole charted window instead of one dot. The root cause was the UI request: the page fetched exactly 200 bars, drew 200 and sent those same 200 closes to `GetIndicatorSeries`, which computes only on the closes it is given (a documented feature-125 contract, not an analysis defect). The fix is "Option B": analysis reports each component's first-value bars through one additive proto field (`ComponentSeries.first_value_bars = 5`, no compute change). The UI fetches D bars (a seeded config key), draws the last W = 200, tail-slices every series through one pure seam, and shows a per-component "Not enough history" pane only when the bars page came back short and P > H. It also added the config key `ui.chart.indicator_history_bars` (default 200, write bound [200, 1000]; seed migration `050_ui_chart_history_bars`) and the marketdata counter `marketdata.ohlcv.out_of_memory_errors`. Shipped behaviour matches the design; the deviations are the pin-formula erratum, operator directives dropping two runbook preconditions, and tooling/verification fallbacks (below). Promoted into `services/xstockstrat-ui/acceptance/fix-indicator-pane-warmup.feature` (all four @AC, `@feature-341`).

- Why P is "first-value bars", not converged lookback (D-7, R-5): the product spec defines P as the bars needed for the first value, EMA/MACD = 1, VWAP = 0, so FR-2 (H < P) can never hide a line that renders today. STOCH P = period (the earliest series, `k`), not period + 2 (O-14). Custom formula P = declared `warmup_period` + 1 (`indicators.proto:174`), 0 when undeclared; `source_symbol`, FUNDAMENTAL and fundamentals-only formulas report 0. A multi-series component uses its earliest series. 0 means fail-open: the UI never shows the notice for 0.
- Why the notice fires only on a short page (D-11, O-4): on a full page the shortfall is unknowable (more history may exist), so a full page degrades to leading gaps. Consequence: with D = 200 a full page never shows "Not enough history".
- Why a seeded config key and not a constant or env (D-18, R-13, R-14, R-16): the DigitalOcean (staging and production share one managed DB) and the homelab (own DB) both run `APPLICATION_ENV` staging, so environment scoping cannot tell them apart; they differ only in which config database they read. A global `ui` key seeded at the safe 200 and raised on the homelab by `set_config` keeps the per-deployment value in config. Branching on `HOST_PROVIDER` (`homelab ? 1000 : 200`) was the proposer's runner-up: no migration or manual step, but it keeps a per-deployment value in source and turns an OTel resource attribute into behaviour. It was recorded as rejected after the adversary agreed, not held for the gate.
- Lock-budget arithmetic of record (D-24, D-25), not re-derivable without the sources: at D = 1000 the implicit `GetBars` window widens from 600 to 3000 calendar days (`defaultBarLookback` slack 3x is the real lock multiplier). One scan takes 8,050-11,680 locks (DigitalOcean at D = 1000; the homelab 1-day-chunk-only figure from the round-5 synth is 8,280-12,000 per scan; the cluster mixes pre-004 1-day chunks with 30-day chunks) against a DigitalOcean budget of 25,600; four scans (2 environments x marketdata pool 2 on the shared cluster) take 32,200-46,720 and fail. DigitalOcean at 200 is unchanged (at most 2,400 per scan, 9,600 at 4 scans). Homelab: `max_locks_per_transaction` 1024 x (`max_connections` 70 + `max_prepared_transactions` 0) = 71,680 slots; 30-day chunks need at most 404 locks per scan (101 chunks x 4 relations), 28,280 at c = 70, so it passes. On stock mlpt 64 the budget would be 4,480 (passes only at c <= 11). The 2,010-2,920 chunk figure used in rounds 2-3 was an estimate. The write term is distinct chunks x 4, not rows. The staleness/DB-miss refetch also upserts about 2,000 rows in one transaction (about 8k locks).
- Why the counter is named `out_of_memory_errors` and not `lock_*` (D-22, O-20): SQLSTATE 53200 is `out_of_memory`, not only lock-table exhaustion (the debate cited fails.md:3060, a 53200 classifier trap); an increment on `marketdata.ohlcv` is read as lock-table exhaustion in the marketdata `CLAUDE.md`, but any other out-of-memory cause also counts. It detects a breach after the fact and does not prevent one. Feature 343 depends on it (operator: one counter, owned by 341).
- Why the pin formula is `(first_value_bars - 1) + _CROSSOVER_LOOKBACK == builtin_lookback_bars`: design.md's `first_value_bars + _CROSSOVER_LOOKBACK` is off by one against its own values (SMA 200: 201 != 200). The spec corrected it to D-7's definition ("first valid index + 1"; SMA 200 -> 200, RSI 14 -> 15). The operator accepted at the execute checkpoint: "Agreed".

The seeding also writes both staging and production rows at 200, including on the homelab, so a deploy alone ships no fix there.
- `HISTORY_CONFIG_TIMEOUT_MS = 3_000` (deadlines.ts) is the spec author's number (design said only "a short timeout"; the shortest existing deadline is 10 s). It landed unconfirmed in sequential mode (no Phase-2 prompt); the log shows no operator confirmation. A wrong value only falls back to 200 (PLAT-N1), but `loadBars` waits for the config read to settle, so a slow config service delays the first bars request by up to this timeout.
- One-shot read, no `WatchConfig`, no new route: it reuses the existing `traderConfigClient.getConfig({ namespace: 'ui' })` BFF forward (`traderBff.ts`), `staleTime: Infinity`. An open tab therefore keeps the old D after `set_config`; reload to pick it up (runbook smoke step).
- Slice seam (O-1, R-6, R-8): a stale cached series would otherwise shift one bar per new bar, so `windowIndicatorSeries` takes times, H and exhaustion from the one series response (never the page's `times` prop) and the last bar's time joins the query key as a string. The hook `select` was rejected because `historyExhausted` and W live in the page.
- Why FR-2 uses `Eyebrow` + `EmptyState` and a new testid `indicator-panel-insufficient` (D-12, R-7): `CardNotice` wraps its own Card and would nest inside the Indicators Card; the existing error pane and `ComponentSeries.error` are not reused because "not enough history" is not an error (error branch keeps precedence).
- Why the counter wraps every returned error including `rows.Err()` (O-19): pgx v5 delivers most server errors through `rows.Err()`, so a wrapper only on the query call would miss them. `QueryRecentBars` is the only bar path on the mockable `r.db` (the others use `r.pool`), so `observeLockBreach` is also unit-tested directly; pgxmock v4.9.0 `CloseError` covers the `rows.Err()` injection.
- Runbook launch design (D-26, D-27, R-17): the homelab launch is read-only preconditions then three ordered steps, and step 3 is an observation after several deep-history symbol-page loads with a positive control (`GetBars` spans or `marketdata.db.pool.empty_acquire_wait`), not a readiness cycle (readiness uses a fixed 400-day window and never runs the 3000-day scan; an absent lazily-bound series cannot be told from a flat one). A failed gate, or 1-day chunks (only after a restore from a DigitalOcean dump), escalates to the operator; "never silently ship 200". `homelab-edge` `verify` asserts only `max_locks_per_transaction`; the runbook depends on a playbook in a second repo (`roles/db_host/tasks/verify.yml`) so a rename there silently breaks the precondition.
