Config's pooled LISTEN client now reconnects (1 s doubling to 30 s cap, single timer, identity-guarded `dropListener`, LISTEN before the boot `reloadAll`, `resyncAll` re-broadcast, one `serial()` chain for reload + notification work). `getConfig`, the two `setConfig` existence-gate queries and ledger `appendEvent` now return gRPC code 13 on a DB rejection. `WatchConfig` registers a `pending` subscriber before the snapshot read, drains a `missedDelta` catch-up DELTA, and every server-side stream failure ends the call via an idempotent `endSubscriber` (`call.destroy({ code: 13, message })`, `configServiceImpl.ts:368-378`). No proto, migration, config key, env var or `index.ts` change. All 11 `@AC-*` are already promoted to the config and ledger durable suites (see Cross-feature signal).

**Why (irrecoverable rationale)**:
- Pooled LISTEN client (fork a) over a dedicated `pg.Client` (fork b): fork (b) needs an `index.ts` edit (feature 266 owned that pool object) and an F-06 budget re-check (+1 direct connection or query pool to 1). The one bug fork (b) would have avoided (see Scars) was fixed by moving `connect()` inside the try. Fork (b) stayed the documented fallback "if the real-Postgres drop check shows the pooled client does not emit `error`/`end`" (design.md@1ed63958:159-163).
- Backoff constants (1000/30000 ms) are code constants, not config keys, because config cannot watch itself (service invariant #1); ledger hardcodes `reconnectDelayMs` the same way (`eventNotifier.ts:35`@1ed63958 design-time anchor; at HEAD the field is `:39`, default 2000 at `:51`, after feature 248) (design.md@1ed63958:224-225). No jitter: one listener per process (design.md@1ed63958:58-59).
- Status code 13 (not UNAVAILABLE 14) for DB failures and stream termination: 13 is the existing convention (`callback({code:13})` in both services) and Node watchers reconnect on any error (design.md@1ed63958:182-183).
- `pending`/`missedDelta` instead of version-gating `lastVersion` or buffering DELTAs: `lastVersion` was read by nothing (recon.md@1ed63958:181-183), and one fresh full-namespace DELTA (CONFIG-1) covers any number of missed ones (design.md@1ed63958:176-179). `lastVersion` was removed.
- `keepAlive: true` was deferred, not rejected on merit: the operator asked for low rework and 266 owned the `index.ts` pool config (design.md@1ed63958:167-168).
- End-call is reserved for server-side failure because of a reconnect storm: ending every subscriber's call on a DB outage (FR-5) makes every platform client reconnect at once, and each reconnect's snapshot hits the same failing DB. Accepted because clients already back off (`69c8554`). The realistic trigger is a DO single-node psql restart, which drops every DB connection in both environments at once (recon.md@1ed63958:188-191, 217-219; old context.md@1ed63958:39-40). The second reason is platform `@AC-6 @FR-6 @feature-210`: a certificate rotation must not end streams (see Runtime-invariant recommendations).
- D-58 is graded SEV-2 as a group member: the surveyor rated it one level lower on its own; it was grouped because it shares the "end the call so the client reconnects" fix contract with D-35 (old context.md@1ed63958:13-14).
- Operator decisions (binding): 2026-10-21 grouped by service+theme from the debt-radar scan, Track C for all SEV-2 (precedent #1264), scope fixed to D-05/D-06/D-35/D-58 (old context.md@1ed63958:16-17, 76-78); 2026-10-22 design gate r2 "APPROVED as synthesized" incl. the reconnect-retry fix (old context.md@1ed63958:253-257); standing: `x-trace-id` propagated with no C-03 waiver, each WatchConfig subscriber carries its inbound trace id via `first(call.metadata,'x-trace-id')` (old context.md@1ed63958:276-278).

**Rejected alternatives**:
- Reuse ledger `EventNotifier` directly (shared package or copy) — lost: no shared Node package; its fixed delay and `onReconnect` API hide `reloadAll` failures from the reconnect path (design.md@1ed63958:164-166).
- Periodic `SELECT 1` keepalive on the listener client — lost: adds a LISTEN-client `query_timeout` trap surface (`fails.md:3006-3021`, feature 248) (design.md@1ed63958:169-170).
- Round-1 `serial` shape `then(fn,fn).catch(log)` — lost: swallowed `reloadAll` failures so the reconnect path never saw them; replaced by a `serial()` that returns the real link and stores a non-rejecting tail (design.md@1ed63958:171-173).
- Per-client `released` flag — superseded by the `this.listener !== c` identity guard, which also drops stale notification events (design.md@1ed63958:174-175).
- Swap in a fresh Map inside `reloadAll` to clear emptied namespaces — lost: changes boot semantics for every namespace; recorded as a limitation instead (design.md@1ed63958:180-181).
- Soft start at boot with an empty cache — lost: every client would get an empty SNAPSHOT; boot stays fail-fast (`connectedOnce` false rethrows, `index.ts` main exits) (design.md@1ed63958:186-187).
- Shared gRPC error helper — lost: keeps `GetSecret` `@AC-16` and the existing early-return shapes untouched (design.md@1ed63958:184-185).
- Per-file `--experimental-transform-types` for the ledger tests — lost: a second runner beside feature 252's compile-then-test runner would collide with its `package.json` (old context.md@1ed63958:362-363).

**Scars & gotchas**:

**Runtime-invariant recommendations (→ /context-constitution)**:
- CONFIG-*: `endSubscriber` is reachable only from the watchConfig snapshot/catch-up chain and the per-subscriber broadcast catch; the `cancelled`/`error` handlers only delete (so a certificate rotation never triggers end-call; platform `@AC-6 @FR-6 @feature-210`). Second reason: ending every subscriber's call on a DB outage triggers a platform-wide reconnect storm, accepted only because the cause is server-side failure and clients back off.
- CONFIG-*: reload and notification work must run through the `serial()` chain so a stale `reloadAll` write can never overwrite a newer `reloadNamespace` write.
- LEDGER-*: a pooled client acquired in a handler must be released with the caught error on failure (`release(err)` destroys the client); at `DB_POOL_MAX=1` a returned broken client poisons every later `AppendEvent`. The promoted ledger `@AC-10` only pins "the acquired pool client is released", not "released with the error", so the durable suite does not guard destroy-on-failure; only the Step 8 unit test does.
