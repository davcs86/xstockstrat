## Archive Synthesis — 2026-08-31 — /sdd-archiver

**What**: Added `SnapshotOfflinePositions` RPC + `manage_offline_account:snapshot_positions` agent op to seed an effective-dated opening baseline per OFFLINE account; extended the shared `pnl.FoldFrom` engine to fold from a seeded lot-map instead of an empty accumulator; added `trading.offline_position_baselines` table; surfaced `source`/`as_of` provenance fields on every `Position` read path (portfolio migration 013 + `positionColumns` constant); implemented statement-sealed realized reset on re-snapshot; wired deregister purge (FR-8) before `account.deregistered` emit. 14 steps across trading, portfolio, agent, and `packages/proto/pnl`.
**Why (irrecoverable rationale)**: (1) **Trading-owned (not portfolio)**: the offline position fold runs inside `ConfirmOrder` (`trading.go:934-980`) via `pnl.Fold`; portfolio only stores the emitted `account.positions.synced` event (`ConsumePositionSyncs`). The baseline change must therefore land in trading and the pnl engine — not in portfolio. (2) **Separate mutable table (not synthetic orders)**: a synthetic sell order seeded as the baseline would corrupt realized P&L by registering as a closing trade. The baseline is a plain mutable table with a composite PK `(account_id, client_snapshot_id, symbol)` + `as_of` DESC index; the ledger's append-only invariant is preserved by never writing the baseline there. (3) **FoldFrom sibling (not modifying Fold)**: `FoldFrom(nil, fills) == Fold(fills)` by construction — extracting `foldInto(accs, fills)` and adding `FoldFrom(baseline, fills)` as a sibling leaves all existing callers byte-identical. (4) **confirmLock serialization (AC-10)**: `SnapshotOfflinePositions` must hold `s.confirmLock(accountID)` around persist+recompute+emit because `ConfirmOrder` already holds the same lock (`trading.go:912`) and the baseline recompute must be atomic with the persist; the extracted `recomputeAndEmitOfflinePositions` producer is explicitly lock-free (caller-holds-lock). (5) **Fail-closed baseline load**: three branches — rows → seeded fold; zero rows → fold-all (no baseline); ERROR → skip-emit, never fold-all on error — guarantees that a DB error cannot silently wipe positions. (6) **Statement-sealed realized reset**: a later `SnapshotOfflinePositions` call reseats realized P&L to 0.00 via replace-not-accumulate `UpsertOfflineRealized` (AC-14); carry-forward realized was rejected because it would misrepresent gains across statement periods. (7) **Deregister purge before emit (FR-8/AC-18)**: `DeleteBaselinesByAccount` runs synchronously in the OFFLINE branch of `DeregisterBrokerAccountSvc` (`trading.go:2758`) and fails the RPC on DB error, before the `account.deregistered` emit — guaranteeing no orphaned baseline rows survive deregistration. (8) **positionColumns parity (C-10(b))**: the `positionColumns` SELECT constant (`portfolio_repo.go:285`) drives both `ListPositions` (`:117`) and `ListPositionsByAccount` (`:498`, behind `buildAccountPortfolio`/`ListPortfolios`) — one edit surfaces provenance on both read paths simultaneously.
**Rejected alternatives**: Synthetic-orders baseline — lost (corrupts realized P&L); lot-lineage provenance — lost (implementation complexity, no observable consumer benefit); provenance-on-portfolio-read-side — lost (spreads the seam, misses the trading-emit; trading is the canonical source); carry-forward realized — lost (misrepresents cross-period gains); lock-inside-producer — lost (`confirmLock` is a non-reentrant `sync.Mutex`; internal acquire deadlocks).
**Scars & gotchas**: (1) **confirmLock non-reentrancy (critical)**: `s.confirmLock(accountID)` in `xstockstrat-trading` is a non-reentrant `sync.Mutex`. Any method called within a `confirmLock` block must carry `// caller must hold s.confirmLock(accountID)` and must never attempt to acquire the lock itself — doing so deadlocks. `recomputeAndEmitOfflinePositions` carries this annotation by design; future callers of it must preserve it. (2) **Absolute-snapshot fail-closed**: `portfolio_service.go:940` `DeletePositionsNotInSync` is called on every `account.positions.synced` event, wiping all positions not in the snapshot; any emitter of that event must be fail-closed on DB errors (ERROR → skip-emit, never emit an empty or partial snapshot that triggers a destructive wipe). (3) **Non-empty user_id in emit (add-ikbr trap)**: `account.positions.synced` (and `account.positions.baseline_set`) must always carry a non-empty `user_id` — the original `add-ikbr-account-support` bug shipped the event without it, causing weeks-later reconciliation failures. The `extractUserID(ctx)` guard in the handler (`handler/trading.go:75`) enforces this. (4) **Cross-remote-branch migration numbering**: trading max NNN across ALL remote branches was `008` → next `009`; portfolio was `012` → next `013`. A local `ls migrations/` would have been unsafe if a feature branch had an unreleased migration (fails.md 2026-07-29/081 trap). (5) **Out-of-repo consumer**: the `xstockstrat-trade-confirm-ingest` skill (named in the product spec) is session/marketplace-managed — not a file in the repo. Updating it is a follow-up outside this PR's reach; the in-repo doc surfaces (mcp-tools.md, service CLAUDE.md files) are the complete repo-side C-14 documentation. (6) **Mixed-lot provenance is symbol-level**: a symbol that has any baseline shares AND any post-T0 confirmed fill → `MIXED`, regardless of how many baseline shares remain (flatten + refill also → `MIXED`). `BASELINE` requires only baseline shares, no post-T0 fills; `ORDERS` requires only post-T0 fills, no baseline shares.
**Permanent deviations**: spec file status updates for Steps 1-4 and 6-7 deferred to the next step's commit (caught up rather than per-step as §5.5 prescribes — no data loss, all outcomes recorded); design-deferred groundings (deregister purge site path:line, portfolio migration NNN, positionColumns parity) resolved at /sdd-spec time via cross-remote-branch scan.
**Cross-feature signal**: (1) Any future feature that emits `account.positions.synced` must be fail-closed on DB errors; the wipe-path at `portfolio_service.go:940` makes an empty or partial emit destructive. (2) `recomputeAndEmitOfflinePositions` is a lock-free producer — future callers must hold `confirmLock(accountID)` before invoking it or the OFFLINE fold will race with concurrent `ConfirmOrder` calls. (3) The `positionColumns` constant is the single column-coverage point for both `ListPositions` and `ListPortfolios`; any new `Position` field added to the DB schema must be added to that constant, not to either read-path individually.
**Deferred follow-ons**: The `xstockstrat-trade-confirm-ingest` external skill needs updating to expose the new `snapshot_positions` operation. The defensive realized-reset branch at `UpsertOfflineRealized` is unreachable via a valid `SnapshotOfflinePositions` call (min qty=0 is valid, but the reset only fires on re-snapshot) — no cleanup needed now.
