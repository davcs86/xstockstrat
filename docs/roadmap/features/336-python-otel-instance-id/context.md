**Why (irrecoverable rationale)**:
- Trigger was a live Grafana finding: the four homelab Python services exported UUIDs, so `{service_instance_id=~"homelab-.+"}` missed 4 of 12 services and the operator wanted one indexed label to select a whole provider. Alternatives were closed: `service.namespace` rejected here and in 332 R-6; Grafana Cloud's OTLP index-label setting is unavailable on the current tier so there is no `host_provider` Loki label; `| host_provider="homelab"` stays the canonical log filter.
- Precedence was verified, not assumed: in SDK 1.45.1 source `Resource.create` merges `ServiceInstanceIdResourceDetector` (random UUID v4) first and the caller's attributes last, so an explicit key wins. The RED failure was a value mismatch, not a KeyError — which proves the UUID is already inside `Resource.create`'s output (Step 2; D-6).
- C-16 sign-off: the reversal of two launched business rules was explicitly confirmed by the operator via AskUserQuestion at the round-1 design gate, 2026-11-12 — 332 `@AC-21` and `@AC-12` are CHANGED, `@AC-19` is only EXTENDED; execute then pre-approved the promotion plan. platform.feature carries only `# Changed by @feature-336`, not the approval.
- A per-instance suffix was dropped because live `target_info` showed one instance per job per provider and the brief DO rolling-deploy overlap (already carried by Go/Node/UI) produced no measured ingest errors; its cost was a 12-runtime change, a new series per container recreate, churn on non-hex hosts and superseding 332's exact-id assertions on 8 services.
- Expected ids in tests (`homelab-indicators`, `unknown-ingest`) stay inline on purpose (D-14/O-12): they are per-scenario expected values, not shared fixtures, so C-13 does not force a conftest constant — recon first recommended the opposite, which shows how easy the wrong reading is; a future C-13 sweep or `/sdd-qa` should not "fix" it.
- Ingest's renamed `test_unrecognised_host_provider_exports_unknown_prefix` deliberately does not test that startup reaches SERVING (D-10/O-9): that clause of 336 AC-3/AC-9 relies on 332 `@AC-3/@AC-4/@AC-13` coverage that startup never blocks. Recon had asked for a per-service unset-provider wire test (AC-3/AC-9 "one per remaining service"); the spec deliberately overrode it — analysis, indicators and agent get the unset case through the unit test's `unset` id (D-16a) and the `HOST_PROVIDER=homelab` run, and only ingest has an end-to-end unrecognised-provider test, so this is not a coverage gap. The `digitalocean` wire stacking is analysis-only because a copied DO wire test would be flagged by jscpd under C-18 (analysis parametrizes or shares a helper); the provider assertion must compare against the parameter, not the literal `"homelab"` (D-9/O-6). The adversary verified before the relabel shipped that `packages/otel/` keys on `service_name`, never `instance`, so no dashboard or alert pins a Python instance value (recon had left it unverified).
- An empty `SERVICE_NAME` would produce `homelab-` while the SDK may export `unknown_service`; the operator accepted this edge with no guard and no test because every deploy surface sets a non-empty literal (D-15).

**Rejected alternatives**:
- Per-instance suffix `<provider>-<service>-<suffix6>` (first 6 hex of the OS hostname when it is a 12- or 64-hex container id, else random) — operator widened scope to all 12 runtimes to carry it, then dropped it as marginal (see Why).
- Trace/span ids as the discriminator — request-scoped; `service.instance.id` is a per-process resource attribute and metric series carry no trace id; the collision guarded is two processes writing one `(job, instance, deployment_environment)` series.
- Reading `HOSTNAME` env (`deploy/homelab/compose.yml:290` sets UI `HOSTNAME=0.0.0.0`, so the OS hostname would have to be read); an unvalidated hostname prefix (junk suffixes); suffix before the service (breaks `homelab-<service>-.+` selection).
- R-1 shared Python helper/package — separate uv projects, new package + four Dockerfile/lockfile changes for one f-string (C-18; `_host_provider` is already copied per service). R-2 `OTEL_RESOURCE_ATTRIBUTES` in deploy specs — breaches 332 `@AC-22` and the CI guard. R-3 test that code-set id beats the env var — YAGNI (CI already rejects that env var in deploy specs).
- Testing AC-4 (identical across starts) by running `_build_resource` in subprocesses — such a subprocess never exports so the test could not fail for the reason AC-4 exists; the test runs the real exporting child twice (O-1→D-5).

**Scars & gotchas**:
- Latent risk not in design: after an interpreter fork the SDK's providers re-run process-dependent detectors and a fresh UUID overwrites a user-set `service.instance.id` (SDK docstring). No service forks today (single `python -m app.main`, thread pools, indicators sandbox uses `subprocess.Popen` with a fresh env-stripped interpreter); any future `multiprocessing`/`os.fork` of a service process would silently restore a UUID on the child's exported id.
- A RED failure mode answers "where the library default lives" without reading the library: KeyError = added downstream, mismatch = inside `Resource.create`.
- The rejected wire-test comment would be 115 chars and fail ruff E501 (`line-length = 100`; `ruff format` does not wrap comments; splitting breaks the 2-line cap) (O-10→D-12). AC-5 ("run with HOST_PROVIDER=homelab") was never exercised because CI sets no `HOST_PROVIDER` while tests read it from the environment — each unit runs the telemetry tests twice, plain and with `HOST_PROVIDER=homelab` (O-11→D-13).
- Doc-verification greps like `grep "relabel" | grep "Python"` break on wrapped bullets (keep both words on one line); `git diff -U0 … | grep -c '^@@'` hunk-count and guard-block-untouched checks only see uncommitted changes — run before the step commit or diff against main-dev, else they pass checking nothing. Steps 3–8 said "apply Step 2's items", risking copying analysis-only `digitalocean` stacking and the analysis default literal into the other services.
