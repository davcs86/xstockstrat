# Context: fix-identity-auth-code-race  (archived 2026-11-04)

**Feature**: ./feature.md
**Status**: launched — archived by /sdd-archiver; verbose specs pruned (recoverable via git history).

## Archive Synthesis — 2026-11-04 — /sdd-archiver

**What**: SEV-2 bug fix (debt-radar D-23 auth-code half + D-21 residual) in `xstockstrat-identity` only. `exchangeAuthCode` no longer consumes a code with an unconditional UPDATE followed by an out-of-transaction refresh INSERT; it keeps its validation as reject-only pre-filters, mints the access token, then calls a new private `redeemAuthCode` (BEGIN; conditional claim `consumed_at IS NULL AND expires_at > NOW() RETURNING`; `issueRefreshToken` in the same txn; COMMIT) and returns tokens only after COMMIT. D-21: `mintOAuthAccessToken` became `mintAccessToken(userId, email, roles, audience?)` and first-party login/refresh now share it and `issueRefreshToken`. Launched 2026-10-30 (PR #1368, df521ff51091a86e813950b34afff09ac4e8821b). No proto, migration or config change. 6 steps, 89 tests green at the last step.
**Why (irrecoverable rationale)**:
- Pattern copied from hotfix `5bd271d` `rotateRefreshToken` (conditional claim decided by row count + same-txn successor insert). The hotfix fixed the refresh race only; the identical auth-code race stayed open until this feature (triage session 2026-10-21).
- Mint happens BEFORE the claim because the `jwtSecret` getter throws when `JWT_SECRET` is unset (IDENTITY-1): a post-COMMIT throw would burn the code and leave an orphan refresh row. Proposal r2 minted after COMMIT; the round-2 synthesis reversed it and the operator approved it 2026-10-22 (design gate r2). Cost: each losing racer signs one token and discards it. Recon fork 2 had said "the mint is pure CPU, so either order works" (recon.md@1ed63958:121); that was wrong because the `jwtSecret` getter can throw (found in round 2).
- D-21 was folded into the security fix "so the D-23 fix reuses a single issue helper that first-party login also uses"; the operator could drop it (AC-4) at design if it read as an unrelated refactor (old context.md@1ed63958:31-33). Step 1 therefore kept calling the old `mintOAuthAccessToken` "so the security fix lands without the refactor" (implementation-spec.md@1ed63958:17-18).
- Explicit NULL `client_id`: design §2 accepted first-party refresh rows storing `client_id = NULL` explicitly as a signed-off side effect (design.md@1ed63958:84-86; AC-4 marked CHANGE under C-16, design.md@1ed63958:261-265). /sdd-spec refined it: refresh already wrote NULL via `issueRefreshToken`, so only login was RED (old context.md@1ed63958:294-297).
- Validation stays ahead of the claim (FR-5: a bad verifier/redirect/client must not burn the code, otherwise an attacker holding only the code could deny the legitimate client). The JS consumed/expiry early-outs are best-effort pre-filters on a stale read and can only reject; only the claim's row count grants. The claim predicates `consumed_at IS NULL` and `expires_at > NOW()` are load-bearing: AC-2/AC-6 exit through the JS early-outs, so only the 20-way race and the `expireAtClaim` test exercise the predicates. Never drop them as "redundant with the JS checks".
- Accepted residual: a lost COMMIT acknowledgement leaves the code consumed and a refresh row written while the caller sees `13` (same as `rotateRefreshToken`).
**Rejected alternatives**:
- Reuse `routePool` for the AC-4 param checks — lost: it records params but has no `connect()`, so it cannot drive `rotateRefreshToken`/`redeemAuthCode`'s transaction; `makeSpyPool` was extended instead (`implementation-spec.md@1ed63958:376-377`, `old context.md@1ed63958:360-361`).
- Mint after COMMIT — lost: mint can throw (IDENTITY-1), burning the code (design.md §1, context 2026-10-22).
- Mint inside `redeemAuthCode` via callback/returned pair — lost: couples the txn helper to JWT minting (C-18); "minting first in the handler closes FR-2 just as well and is simpler" (design.md@1ed63958:169-170).
- Delete the JS early-outs — lost: rework, breaks existing exchange tests, lets stale codes tie up identity's 2-connection pool.
- Shared `withTransaction` helper — lost: edits hotfix code, widens diff; only if jscpd forced it and only after asking the user (never forced: jscpd found no clone between `redeemAuthCode` and `rotateRefreshToken`).
- Single-statement CTE claim+INSERT — lost: departs from the rotateRefreshToken pattern, awkward with `issueRefreshToken`, harder to fault-inject.
- `SELECT ... FOR UPDATE` then validate then UPDATE — lost: probes and failed validations would hold a row lock and a pool connection.
- Validation predicates inside the claim WHERE — lost: PKCE cannot be checked in SQL, and a mismatch would be indistinguishable from "consumed", weakening the FR-5 tests; also a larger rewrite (design.md@1ed63958:179-181).
- Committed opt-in real-Postgres test — lost: one-off per-feature DB rig (fails.md:2255, C-18).
- Separate first-party mint helper — lost to making `aud` optional on the existing helper (FR-6/FR-8, IDENTITY-4).
- Third ad-hoc fake for login/refresh param checks — lost to an additive params-recording change on `makeSpyPool` (C-18).
