**Status**: launched — archived by /sdd-archiver; verbose specs pruned (recoverable via git history).

## Archive Synthesis — 2026-09-02 — /sdd-archiver

**What**: Shipped a net-new `mcp_client` server-side signal `source_type` in `xstockstrat-ingest` — the first server-side outbound HTTP client, the first `GetSecret` call, and the first background poll loop that service has ever had (before this, the `noop`/`mediated_*` extractors were never driven server-side; ingest was inbound-only). The MCP endpoint/tool ride the existing `config_json` (Struct), the bearer is an encrypted config secret (`ingest.mcp_credential.<slug>`, feature-147 machinery), a paced `asyncio` loop resolves the bearer and calls the external MCP tool over Streamable HTTP, parses a fixed xstockstrat response contract into `ExternalSignal`s, and ingests through the unchanged `IngestSignal` path. **Zero proto change.**

**Why (irrecoverable rationale)**: The whole design hinges on "no new proto field": `source_type` is a runtime-extensible string governed by a DB CHECK (not an enum), and source-specific config (`mcp_endpoint`/`mcp_tool`) rides the existing `config_json` Struct rather than typed proto fields — deliberately, to avoid proto churn and, critically, to keep the bearer off the wire/logs (a proto `bearer_token` field would be a plaintext secret in transit, and `config_json` is returned verbatim by `ListSignalSources`). The bearer goes straight to encrypted config; ingest stores only the `credentials_ref`.

**Rejected alternatives**: bearer on a new `signal_sources` DB column (violates feature-147 secret-at-rest + redaction; repeats the migration-009/076 plaintext-in-a-broadcast-table trap); pass the token through `config_json` and let ingest write the secret (`config_json` is returned verbatim by `ListSignalSources` so plaintext leaks; also forces a needless ingest→config write edge); typed `mcp_endpoint`/`bearer_token` proto fields (breaks "no proto change" + a proto bearer field is plaintext on the wire); agent-mediated pull reusing `mediated_*` (the feature's purpose is unattended in-service pull with no agent in the loop); a per-source field-mapping DSL in `config_json` (a fixed response contract avoids a speculative mapping/validation surface); a compensating saga to clean an orphaned secret on register failure (secret-first ordering makes a failed register leave only a harmless redacted orphan); a thin httpx JSON-RPC MCP client instead of the SDK (held as fallback, ultimately not needed once the installed `mcp` wheel was confirmed to expose a header-injectable Streamable-HTTP client).

**Scars & gotchas**: The `mcp` package is a non-reference distribution (non-standard module paths `mcp.server.mcpserver`; deps `httpx2`+`mcp-types`), so its client-side API cannot be assumed from reference-SDK docs and had to be verified by inspecting the wheel; the pin drifted `mcp==2.0.0` (spec) → `2.1.1` at `uv lock`, API re-verified. Bearer injection works only via the **low-level** `streamable_http_client(url, http_client=httpx2.AsyncClient(headers={"Authorization": ...}))` — the high-level `Client(url)` cannot inject headers. `poll_interval_seconds` is operator-settable via config-ui, so `0` busy-loops the query loop → shipped a loop-side `max(interval, 1)` clamp rather than a `SCALAR_BOUNDS_REGISTRY` bound.

**Permanent deviations**: design/spec assumed `SetConfigRequest.is_secret` → shipped sets `ConfigValue.is_secret` (the proto has no such field on the request; the config backend reads `value.is_secret` on write). design implied a `/sources` page server-wrapper to thread the client-hidden env → shipped the config-ui BFF filling an `Environment.UNSPECIFIED` SetConfig with the deployment's native scope (`nativeConfigEnvironment()`) so the secret write lands on the correct env. design named exact-`keys` grants → shipped a new `keyPrefixes` concept on `SecretCallerGrant` because ingest's per-slug `mcp_credential.<slug>` keys are dynamic and can't be enumerated (marketdata's exact grant + the fail-closed default preserved).

**Cross-feature signal**: Establishes a reusable **secret-first two-write** orchestration for "register an entity that owns a credential": write the encrypted config secret first, then register with only its `credentials_ref`; a failed register degrades safely (a harmless redacted orphan). Used identically by the agent tool and the config-ui BFF. The `mcp` non-reference-distro verification requirement recurs across every feature touching the SDK (009, this one).

**Deferred follow-ons**: feature-093's mediated-credential path is still unimplemented — `extract_website_content` still RAISES for `mediated_*` sources with `has_credentials=true`; this feature built credential resolution for `mcp_client` only. Config migration `025_ingest_mcp_client_keys` carried a merge-order dependency (apply after `022`/`023`/`024`).
