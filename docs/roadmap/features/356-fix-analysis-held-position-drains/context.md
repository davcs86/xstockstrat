## Archive Synthesis — 2026-11-18 — /sdd-archiver

**What**: SEV-3 bug fix, analysis only. The two portfolio `ListPositions` held-position drains (`live_loop._drain_held`, `servicer._drain_held_symbols`) used to trust `next_page_token`, stop silently at 50 pages, and return the rows collected so far when a page failed. Both now go through one shared `_drain_positions_paged(stub, user_id, metadata) -> list` in `app/handlers/servicer.py` that raises `_PositionsPageError(Exception)` on any page-body error, a non-empty token equal to the one sent, or cap exhaustion (WARNING naming the user and 50 first). The live loop counts `drain_failures{source=held}` once and re-raises; its cycle catches `_PositionsPageError` before `except ValueError` and skips that owner via a per-cycle `failed_owners` set. `ScreenSymbols` marks no row `held` and still returns. `_compute_opportunities` and `entry_backfill.py` are unchanged (the raise reaches existing handlers). The daily opportunity refresh gained one call site, `record_opportunity_recompute("full","failed")` plus `exc_info=True`, in its per-user catch. Shipped in PR #1577 (squash `64478216`, commit date 2026-11-17); launched 2026-11-18 via promotion PR #1580 (source: this file's CI session; feature.md). No proto, migration, config, pool or other-service change; features 351, 353, 354 untouched.

**Why (irrecoverable rationale)**:
- Shared helper vs in-place was an operator-delegated fork (triage, 2026-11-17: "decide in design"; paraphrase in context, not a verbatim quote). Design chose one helper (D-1) because the two loop bodies were identical and every RED fake and the token rule would otherwise be duplicated (DRY). The helper returns rows and each caller reduces (set vs summed `abs(market_value)` per symbol); `max_pages`/`page_size` parameters were refused as YAGNI because no test patches the drain constants (R-4).
- The typed error is deliberately not a `ValueError` (D-2). The live-loop cycle's `except ValueError` means "ownerless strategy, skip"; a `ValueError` subclass would have been treated as that skip and never cached as a failed owner. Broad `except Exception` in the cycle was refused (R-2/D-3) because it would also change the out-of-scope `_drain_watchlist` / `_drain_owner_signals` handling. The helper's `try` wraps only the page body (await, row collection, token read) so the guard's own `_PositionsPageError` is never re-wrapped into misleading cause chains (D-6, round-2 adversary).
- The metric stays inside `_drain_held` (D-4): it records `drain_failures{held}` and re-raises without logging; the caller logs the owner WARNING and the helper logs the cap WARNING. That keeps `@AC-16 @feature-294` once per failed owner per cycle with no double count. Side effect nobody removed on purpose: the entry backfill (which calls `_drain_held`) also increments that counter on a boot-time failure.
- Later strategies of a failed owner are skipped without another log line; the single WARNING names only the first strategy and the owner (D-10). FR-4 asks for one WARNING per owner; collecting every skipped strategy id like the backfill does was refused as extra code (CLAUDE.md rule 2).
- Fail-closed bound is 5,000 positions per owner, not 50,000: portfolio clamps any `pageSize > 500` to 100 (`portfolio_repo.go:137-138`), so the requested 1000 is ignored; an owner above 5,000 positions is skipped every cycle. Portfolio pages by a strict keyset cursor (`portfolio_repo.go:166-167`), so a correct server cannot re-serve the token it was sent: the equal-token guard defends against a server defect or a fake and is not an expected production path (D-8). `next == sent` does not catch an A→B→A token cycle; the 50-page cap is its backstop.
- Daily-refresh counting (D-11) was an operator steer that reversed R-6 ("no new metric"). The path: round 2 recorded the daily refresh as "counted as a failed loop-tick item" (D-7, repeated in the draft FR-4 wording); round 3's adversary showed that is false (`_log_items_tick(loop, t0, total, failed)`, `servicer.py:377-382`, emits no failed count and uses `failed` only to skip the tick when `failed == total`: partial failure writes an ordinary `loop tick ok`, and only an all-users failure writes no tick) and petitioned P-1 (D-7) and P-2 (D-5). The operator then required the daily refresh to COUNT a failed user as a metric, reusing an existing instrument and label set. Adopted: one call site on `recompute{kind=full,outcome=failed}` in the per-user catch, with no user attribute. Rejected forms: a new `kind=daily` label value (R-10; `kind` means recompute scope and the daily pass is a full recompute, and it stays the clean upgrade if a daily-staleness alert is ever written), counting inside `_compute_opportunities` (R-11, double-counts the kick path at `servicer.py:4957`), recording a daily-path `ok` (R-12, beyond the steer and would change the meaning of the kick-path `ok` series), and an empty-held-map fallback (R-5, held symbols would rank 0.0 in a normal-looking queue, the silent partial result fails.md:3311-3312 forbids).
- Accepted consequences recorded rather than coded: (a) a transient held-drain failure at boot leaves that owner's entry-backfill `last_entry_at` unseeded until the process restarts, no retry (`entry_backfill.py:52-58,142-159,199-202`); (b) a portfolio outage skips every owner in the live loop each cycle (counter +1 and one WARNING per owner per cycle); (c) `ScreenSymbols` loses its `held` badges but the request is not aborted; (d) the daily refresh leaves a failed user's queue stale for about 24h, counted on `recompute{full,failed}` plus a WARNING with traceback, with the schedule still advancing; if every user fails, the counter rises by N, no `loop tick ok` is written and all queues stay stale; (e) `recompute{kind=full,outcome=failed}` now merges a kick-path failure (retried on the next read) with a daily failure, and also counts non-drain per-user errors (`owner_metadata` ValueError for a system or empty uid, lock or replace errors) — accepted scope; `ok` is kick-path only, so no failed/(ok+failed) ratio over `kind=full` is meaningful (caveat now at `services/xstockstrat-analysis/CLAUDE.md:327`; the `loop tick ok` sentence at `:326` is deliberately untouched).
- The typed error also has a second reason (D-2; recon): an untyped raise from `_drain_held` would escape `_run_cycle` into the `run_forever` catch-all (`live_loop.py:351-352` at spec time) and abort every owner's cycle, not just the failed owner's.
- Accepted risk: the live-loop held drain now reads the servicer constants `_MAX_DRAIN_PAGES`/`_BAR_PAGE_SIZE`; `live_loop._DRAIN_PAGES`/`_DRAIN_PAGE_SIZE` were kept only for the sibling drains. The values are equal today but can drift, and editing `live_loop._DRAIN_PAGES` no longer changes the held drain.
- Wrapping every page exception turns a programming error such as an `AttributeError` into an owner skip; the original is kept as `__cause__`. Accepted.
- The un-guarded `gather` at `_compute_opportunities` (`servicer.py:5365`) leaves sibling drains running when the held drain raises. Existing behaviour, left alone to avoid colliding with feature 308's edit of the same function.
- `produced-signals.tsv` row `analysis_opportunity_recompute_total` exists by operator mandate (r4 gate), not because the code needs it: no alert or dashboard queries it (`packages/otel/CLAUDE.md:8-9`), and it is the first counter (`_total`) row in a registry of histogram `_count/_bucket/_sum` and `target_info` rows, so it sets no convention. Verification was moved to /sdd-spec rather than made a PR gate (R-14: it would hold a SEV-3 fix behind a lookup for a row nothing consumes) and was scoped to an environment label (R-15: alerts key on the short `service_name`, OTEL-1). Spec-time result (Grafana Cloud MCP, datasource `grafanacloud-prom`, 30d): name `analysis_opportunity_recompute_total` = 7 series, all `deployment_environment="staging"`, `kind=full`, `outcome=ok`; production returned nothing and no `failed` series existed yet (a counter exports only after its first `add`). Name matched the expected one, so the row was written.
- The `@AC-51 @feature-294` scenario text was left unedited (D-16): its Given ("a background full opportunity recompute that fails once") and Then already cover both the kick path and the daily catch; design records an EXTEND naming `servicer.py:4957` and the daily catch, and the existing `test_analysis_tick_telemetry.py` AC-51 test stays kick-path-only at exactly 1.
- D-9 pre-RED fake sweep result (done at spec time): no existing fake that reaches a held drain returns a truthy shared token; each returns an EOF page, or the path never reaches a drain because `_portfolio` is None (`make_servicer`, `_svc()`, `_make_loop` default). Only `test_ac16_failed_held_drain_counted_without_owner` had to flip, which is why Steps 4+5 were one atomic commit unit.
