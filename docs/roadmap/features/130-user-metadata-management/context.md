# Context: user-metadata-management  (archived 2026-08-19)

**Feature**: ./feature.md
**Status**: launched — archived by /sdd-archiver; verbose specs pruned (recoverable via git history).

## Archive Synthesis — 2026-08-19 — /sdd-archiver

**What**: Shipped self-service user-profile metadata (phone, display_name, JSONB metadata; email/user_id read-only) on the identity service, surfaced through a UI page at `/accounts/profile` and two MCP tools (`get_user_metadata`, `set_user_metadata`, tool count 22→24). The most consequential outcome was a deliberate architectural fork inside identity: its two new self-management RPCs derive the caller from the propagated `x-user-id` gRPC metadata header (C-03), whereas every pre-existing identity RPC reads user_id from the request body. This is the first use of `call.metadata` anywhere in identity. Recon initially recommended the opposite (accept user_id in the request body, extend the config-ui BFF); the user steered against both, and the design overrode recon on three points.

**Why (irrecoverable rationale)**: Self-only enforcement routed through `x-user-id` metadata (not a request-body field) because a request-body userId is an IDOR surface — the caller could name any user; deriving identity from the propagated, edge-injected header makes self-only enforcement structural (user steer from round 1). Email excluded from `UpdateUserMetadataRequest` proto *entirely* (not just hidden in consumers) because email is the login credential (`WHERE email = $1`); allowing mutation without re-auth is a credential-change security gap. The proto absence is deliberate — a future agent seeing "no email field" should read it as a security decision, not a gap to fill.

**Rejected alternatives**: `/config-ui/profile` (the original product-spec FR-6 location) — the config-ui BFF router serves only ConfigService + IngestService; wiring IdentityService in is cross-service contamination, and /accounts already owns identity-adjacent surfaces via plain REST. Request-body userId matching existing identity RPCs (also what recon recommended) — lost to the C-03 header-propagation steer. Editable email — credential-change security gap; if ever wanted, belongs in a dedicated ChangeEmail RPC with password confirmation. Full BFF Connect-RPC router for /accounts — overbuilt; /accounts has only 3 routes. Third local copy of backendHeaders in the profile route — extracted `restBackendHeaders`, which also closed a pre-existing DRY finding.

**Scars & gotchas**: The impl-spec's own authz unit tests contradicted the shipped authz contract — the spec expected `userIdFrom` to throw UNAUTHENTICATED and `first` to return undefined, but shipped `authz.ts` returns empty string on absence and the handler does the guard (returns gRPC code 3); tests adjusted to the empty-string contract. Read-only fields (user_id, email) render inside *disabled `<Input>` elements*, not plain text, so planned `getByText` E2E assertions failed; shipped tests use `getByRole('textbox')` + toHaveValue/toBeDisabled. Step 7 needed a second DRY extraction beyond restBackendHeaders — a `toProfileJson` helper — to satisfy the DRY guard rail on duplicated GET/PUT response shaping. `COPILOT_MCP_TOOL_COUNT` was already stale at 18 while prose claimed 22 — the numeric tool-count surface had silently drifted out of sync with the five prose surfaces; this feature caught it up to 24.

**Permanent deviations**: design said the agent client is a class with methods (`XStockStratClient.get_user_metadata`) → shipped module-level async functions in client.py (the existing client is module-level, not a class; smoke tests import the functions directly). product-spec FR-6 said `/config-ui/profile` → shipped `/accounts/profile` (BFF-contamination reasoning above; product-spec was reconciled at spec time but that reconciled file is pruned, so the "why not config-ui" is captured here).

**Cross-feature signal**: Agent tool count is duplicated across 6 surfaces (5 prose: tools.py:4, agent CLAUDE.md:30, mcp-tools.md:3 and :37, copilot.ts prose — plus 1 numeric COPILOT_MCP_TOOL_COUNT), and the numeric one had already drifted; every agent-tool feature must touch all six (overlaps trigger-backfill-mcp-tool, fix-mcp-config-key-registry). The authz.ts minimal-subset-of-config pattern is now the second instance (config was first) of a leaf Node service extracting first/userIdFrom metadata accessors — a reusable shape for any future self-management RPC.

**Deferred follow-ons**: Migrate the old identity RPCs (listAuthorizedApps, revokeAuthorizedApp) from request-body userId to the metadata pattern to end the dual-sourcing fork (documented via JSDoc in identityServiceImpl.ts). Dedicated ChangeEmail RPC (with password confirmation) if email editing is ever wanted. Narrow the `call: any` typing in identity handlers to `ServerUnaryCall<Req,Res>` for compile-time metadata safety. Out-of-scope forward pointers: admin-over-others metadata, email/phone verification, notify-service routing off metadata.
