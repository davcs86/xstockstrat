# Product Spec: trading-state-machine-invariants

**Created**: 2026-08-04

---

## Problem Statement

Hand-written unit tests for the order lifecycle only cover the specific sequences their authors
thought of. The invariants that must hold under *any* sequence of fills, cancels, replaces, duplicates,
delays, and crashes — the ones that actually protect live capital — are not exercised by example-based
tests and can regress silently.

## User Story

As the platform, I want property-based tests that generate long randomized order-lifecycle event
sequences (including duplicates, reordering, delays, and crashes) and assert core safety invariants
hold under every one of them, so a regression in the state machine is caught before it reaches
production.

## Functional Requirements

FR-1. Model the order lifecycle for property-based / model-based testing, driven by the feature-103
broker simulator's scripted event streams.

FR-2. Assert, across randomized sequences: filled quantity never decreases; filled quantity never
exceeds requested quantity; a terminal order never returns to a working state; one broker fill produces
exactly one ledger economic event; position quantity equals the sum of authoritative fills after
reconciliation; a canceled order is never later treated as safely canceled if a race produced a fill;
closing a position never creates an unintended short position; protective-order quantities never
exceed the open position; OCA siblings never both produce unaccounted exposure changes; no live
position is classified as protected unless protection is broker-confirmed.

FR-3. Generate long randomized event sequences including duplicate events, out-of-order delivery,
delayed delivery, and mid-sequence service restarts.

FR-4. Run in CI on every relevant PR to `xstockstrat-trading` (not just at release time).

## Out of Scope

- Building the simulator that generates these event sequences — feature 103.
- The crash-injection points themselves for restart scenarios — feature 105 (this feature consumes
  restart as one input to its generated sequences; 105 is the dedicated crash-consistency suite).

## Acceptance Criteria

1. Every invariant in FR-2 is encoded as a property assertion and runs against randomized sequences
   generated by the feature-103 simulator.
2. A deliberately-broken invariant (mutation test) is caught by the suite before merge.
3. The suite runs in CI on every PR touching the `xstockstrat-trading` order lifecycle.
