**Why (irrecoverable rationale)**:
- Severity and track: SEV-3 because the defects are non-financial; the https defect is a credential-exposure risk only on misconfiguration (an `http://` URL sends the bearer app key in clear text). Feature 338 was not on `main` (`git show origin/main:…/commsgunClient.ts` failed at triage), so the bug was dev-only, hence Track C. Triage recommended design depth `skip`.
- Operator decisions (2026-11-15, carried from the task and recorded in context.md): pinned-mode missing key is a bug and must raise the incident; 408 must retry. In the review session the owner said, verbatim as context.md quotes it: "fix all, even the https check" — this is the sign-off that widened defect 1 from a bare `https:` check to the whole webhook URL rule minus its allowlist, and that added defect 6 (text cap) to the same PR. All of this was fixed test-first.
- https cannot break a valid deployment, so no owner question was needed: the enqueue host is always served over TLS (the edge serves `*.<magicdns_base_domain>` with the ACME wildcard certificate and the policy grants only tcp:443; source is 338 `recon.md` § Tailnet path and `operations.md` first-deploy check; 338's recon is now pruned).
- The https/URL rule lives once, in `commsgunSettings` (read on every dispatch and every attempt). A non-conforming URL reads as unset and is routed by the existing unset-URL logic. Reusing the webhook rule by extracting `checkHttpsUrl` (no duplicate rule; existing webhook URL-rule tests unchanged and green) means loosening it also loosens the commsgun check (now stated in NOTIFY-14).
- Subject cap evolved: the first session capped at 998 UTF-8 bytes on a code-point boundary because the producer's `SubjectMaxLen` could not be read (session scope limited to this repo) — bytes <= 998 also implies runes <= 998. A follow-up session read `davcs86/commsgun` @ `5c0c129` (public; anonymous clone): `api/internal/enqueue/validate.go#emailContent` rejects a subject that is empty, contains CR or LF (`ContainsAny(subject, "\r\n")`) or has `utf8.RuneCountInString(subject) > constants.SubjectMaxLen` (998). The cap was changed to 998 code points (JS `for...of`/spread iterates the same code points Go counts as runes) so non-ASCII titles are no longer over-truncated; RED then GREEN on the updated @AC-2 test. An empty subject cannot occur because the subject always starts with `[severity] `. Re-read at commsgun `4e3e58d`: enqueue code changed only by refactors since `5c0c129`.
- Review against commsgun `4e3e58d` and webhooks-mcp `c04b851` found no conflict with either producer; webhooks-mcp C3 (retry 503; 404/413/422 final) is covered by notify's webhook classification.
- Text cap arithmetic: text gets 256 KiB − 8 KiB of JSON-escaped bytes plus a `[truncated]` line. The 8 KiB reserve covers a 998-code-point subject at <= 6 escaped bytes (5988), a <= 254-character recipient at <= 6 (1524) and the JSON keys (~60). The cut is in the shared renderer, so SendGrid gets the same subject and text. Rows already queued keep their stored subject/text (NOTIFY-17: stored content is byte-identical on retry), so the fix does not repair rows queued before it.
- Pinned-mode incident reuses the `auto` trigger (key absent, or two consecutive resolve failures) and title; the body says the rows stay queued instead of "goes through SendGrid". Existing @AC-25 (pinned, absent key) now expects 2 alerts: the row's own alert plus the new standing incident. The pinned-mode alert explains the https rule only when `commsgun.enqueue_url` is the missing key.
- 408 uses error class `408` (outcome `http_error`), the same as the webhook worker (`webhookWorker.ts#RETRYABLE_STATUSES`); Caddy in front of commsgun can send 408 (edge timeout). 338 had classified 408 as `4xx` permanent because its D-7 retried only 429/5xx.
