## Archive Synthesis — 2026-11-18 — /sdd-archiver

**What**: SEV-2 bug fix (Track C, `**Type**: bug`) in `xstockstrat-portfolio`: `WatchlistRepo.ListByUser` now returns `nextToken = wls[pageSize-1].WatchlistId` (the last RETURNED row) instead of the look-ahead row `wls[pageSize]`, so the strict-`>` keyset on the next page no longer skips one list at every page boundary. The `pageSize+1` look-ahead stays (only decides "more?"), so an exactly-full last page and an empty result both return `""`. One incidental production-identical change: the page query now reads through the mockable `r.db` instead of `r.pool` so the first `ListByUser` unit tests are possible. No proto, migration or config change; token format (a bare `watchlist_id` UUID string) unchanged. Landed as one `**Lands with**` service+test unit (commit `c20cd61`) via squash PR #1566 -> `main-dev` (`149351d`); promoted to `main` via PR #1573. The defect report's mixed-fleet claim was confirmed in recon, not just asserted.

**Why (irrecoverable rationale)**:
- Token and predicate must agree; the bug is their mismatch and the token side is the one fixed (D-1). Precedent is `services/xstockstrat-marketdata/internal/repository/marketdata_repo.go:954-958` (`last := out[pageSize-1]`). `QueryBars` in the same file uses an inclusive `>=` and is correct in its own right — do not "harmonize" it (O-5, R-2). The recon/ledger citation `marketdata_repo.go:716-766,808-820` (insights.md:3547/3548) had drifted; `:954-958` is the corrected one (the ledger is append-only, so the stale cite stays there).
- **No mixed-fleet shim (D-7).** Both token kinds are bare UUIDs. An OLD token sent to a NEW server resumes after the old look-ahead row, so that row is skipped once (the same loss as today); a NEW token sent to an OLD server resumes correctly. This asymmetry is why no version-tagged token was added; recon also noted analysis drains complete in one cycle, so only a drain in flight at deploy time is exposed. Contrast sibling 353 (`fix-listpositions-nextpagetoken-skips`), which needed a composite cursor for a non-unique `symbol` key and rejects legacy tokens as `InvalidArgument` (deliberate departure); 354 keeps the unique `watchlist_id` PK keyset (`migrations/007_watchlists.up.sql:6-14`, no ties) and adds no token validation. A malformed `page_token` still surfaces as the existing `$2::uuid` cast error -> INTERNAL, unverified whether at Query or at `rows.Err()`; pre-existing, out of scope.
- **Accepted risk that looks like a bug:** real-world exposure at default config was low — `watchlist.max_per_user` = 50 < every consumer's effective page (UI 50; analysis asks 1000 and the repo clamps to 100; agent default 100), so default-config owners never crossed a boundary; the loss showed for a small explicit agent `limit`, or if the cap were raised (recon.md Risks); feature 351's context.md:72 adds legacy over-cap data as another route to the analysis-universe loss. No source gives a reason for keeping SEV-2 (triage and the report say only "silent-data-loss-in-pagination"); inference: the agent `list_watchlists` docstring "Pagination is stable across pages" (`tools.py:2155`) was false at page boundaries and became true with no edit. Owners with more than 100 lists are now drained losslessly by analysis.
- **Why the page query moved to `r.db` instead of a pure helper (R-1):** a pure `pageAndToken` helper would be a single-caller unit (C-18) and leave the SQL, args, LIMIT and bindings call untested offline. The seam is prod-identical because `NewWatchlistRepo` sets `db: pool` and is the sole constructor (D-3).
