## Archive Synthesis — 2026-08-16 — /sdd-archiver

**What**: Introduced a durable `trading.order_intents` table and `IntentState` lifecycle field into `xstockstrat-trading` so the trader UI's PlaceOrder/ReplaceOrder/CancelOrder calls execute at most once despite network retries, timeouts, or a mid-request redeploy. Scope cut sharply at story time: automated UNKNOWN reconciliation, close/emergency-flatten commands, and downstream features 102/104/105/107 were all demoted — the human-initiated UI flow is the only protected path. Seven adversarial design rounds; user extended the default 5-round cap twice to close genuine correctness gaps.

**Why (irrecoverable rationale)**: In-process per-intent keyed `sync.Mutex` was rejected in round 2 because its sole safety justification ("single instance_count: 1") is unverifiable against DO App Platform's actual rolling-deploy overlap mechanics — a process-boundary event is exactly when the feature must protect. DB-only mechanism (`INSERT ... ON CONFLICT DO NOTHING RETURNING` + optimistic CAS reclaim) is correct at any instance count. `PlaceOrder`'s intent ID is client-nonce-seeded (not content-hashed) because a content hash collapses a deliberate duplicate order with a lost-response retry — the exact failure mode this feature must not introduce. `IntentState` is an orthogonal field (not a widened `OrderStatus` value) because an order can be simultaneously `PARTIALLY_FILLED` and intent-uncertain — one enum cannot express both axes. The late-broker-response race is an accepted v1 limitation: the CAS terminal write cleanly loses to a prior sweep reclaim (0 rows affected), and the real broker response survives only in the `order_intent.late_response_conflict` ledger event. Three ledger events ship: `order_intent.reclaimed_unknown` (sweep reclaim), `order_intent.late_response_conflict` (broker response arrived after reclaim), `order.broker_call_uncertain` (timeout before any response) — emitting `order.broker_rejected` on a timeout would destroy its "definitely rejected" semantics. This three-event taxonomy is not recoverable from the code alone. `order_id` in `order_intents` must be populated at INSERT time for PlaceOrder (not deferred to `FinalizeIntent`) because: (a) a crash-then-sweep-reclaimed intent must be joinable back to its already-visible `trading.orders` row for FR-4's UNKNOWN-distinct requirement; (b) the `order_intent.reclaimed_unknown` ledger event must key on `order_id` per platform convention. `computeStaleThreshold` derives the staleness threshold live from WatchConfig on every call (deliberately NOT cached) because a stale cached threshold could fall below a live-raised `broker.timeout_ms`, causing premature reclaim of a genuinely in-flight order.

**Rejected alternatives**: In-process `sync.Mutex` (unverifiable single-instance premise, zero protection across process boundary). `ORDER_STATUS_UNKNOWN` widened enum (can't express "PARTIALLY_FILLED AND intent-uncertain"). Content/time-bucket hash for `PlaceOrder` intent ID (collapses deliberate duplicate with lost-response retry). Third "still processing" rejection code (`codes.Unavailable`) (un-specced new client-visible behavior). Single unified ledger event (operators grep on event type first). Day-one hypertable for `order_intents` (rate profile doesn't justify; revisit trigger ~500k rows).

**Scars & gotchas**: IBKR has NO broker-side dedup at all (`ibkr.go:116-169` sends no client-order-id) — the platform-level `order_intents` table is IBKR's *only* dedup mechanism. IBKR `cOID` field name confirmed via live web search (IBKR Campus public docs); max-length NOT found in public docs — `"xss-"+UUID` (~40 chars) proceeds conservatively. PlaceOrder ordering: `InsertIntent` must follow all of feature 100's pre-broker gates AND be gated on `!requiresApproval` — the approval path must never touch `order_intents`. `resolveAccount` single-account-fallback bug: iterated the map but never captured the key; signature widened to 3-tuple. `internal/repository` has zero `*_test.go` files and no DB-mocking library — behavioral proof routes through `classifyIntentLookup` (pure function) + `scripts/integration-test.sh`. Sweep interval default corrected to 5000ms (matching `trading.fill_poller.interval_ms` precedent), not 30000ms stated in rounds 4-5. Sweeper (`sweepOrderIntents`) deliberately does NOT call `broadcastOrder` — UI polls at `refetchInterval: 5_000` ms, same order of magnitude as sweep interval; explicit deliberate omission at design round 5, not an oversight. `StreamOrderUpdates` sets `IntentState` inline from writer's own just-written value, without re-running the LATERAL-join precedence query — a narrow consistency gap explicitly accepted as "single-human-operator usage today." `STATUS_VARIANT: Record<string, ...>` in `orderShared.tsx` was deliberately left non-exhaustive — the pre-existing TypeScript fallback `OrderStatus[status] ?? 'UNKNOWN'` produces the string label `'UNKNOWN'` for unrecognized values, which is COMPLETELY SEPARATE from `IntentStateBadge`'s "Uncertain — verify with broker" label. Playwright `global-setup.ts` runs `startMockBackend()` once — the in-memory `clientOrderId` Map is shared across all specs and workers for the run's lifetime.
