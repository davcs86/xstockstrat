## Archive Synthesis — 2026-08-31 — /sdd-archiver

**What**: Added `manage_account` (register / update_credentials / deregister) and `list_accounts` MCP tools to `xstockstrat-agent`, wiring the four pre-existing trading RPCs (`RegisterBrokerAccount`, `UpdateBrokerAccountCredentials`, `DeregisterBrokerAccount`, `ListBrokerAccounts`) through a `_BROKER_TYPE` enum map and a shared `_account_to_dict` helper; migrated `register_offline_account` to the same helper; added a `BrokerAccount` descriptor-parity test; synced all six tool-count surfaces (including `COPILOT_MCP_TOOL_COUNT` in xstockstrat-ui). No proto, config, or DB changes — the agent is the only service touched (all four RPCs pre-exist in `trading.proto`).
**Why (irrecoverable rationale)**: (1) **No proto/DB changes**: all four trading RPCs already existed in `trading.proto:217-286`; the feature is purely an agent consumer, not a service change. (2) **register rejects broker_type=offline** (operator decision at design gate): offline accounts have a dedicated creation path (`register_offline_account`); conflating creation via `manage_account:register` would bypass the offline-specific validation path — one creation path per kind is the enforced invariant. (3) **deregister stays unified**: the trading backend intentionally supports `DeregisterBrokerAccount` for OFFLINE accounts (`trading.go:2754-2761`) — no client-side gate needed. (4) **No client-side credential validation**: `UpdateBrokerAccountCredentials` rejects OFFLINE at the backend (`trading.go:2267-2270`) with `FailedPrecondition`; credentials JSON is validated server-side (`:2257`). Adding a client guard would duplicate enforcement and risk divergence. (5) **`_account_to_dict` helper**: the existing `register_offline_account` used an inline `MessageToDict` call; migrating it to the shared helper is behavioral-parity, not a behavioral change — `BrokerAccount` has no credential field (`trading.proto:217-237`), so `MessageToDict` is structurally credential-safe at any call site. (6) **COPILOT_MCP_TOOL_COUNT sync** (operator-approved deviation): the ledger (fails.md entry RC-1) mandates syncing all six tool-count surfaces on every agent-tool change; `xstockstrat-ui/src/lib/copilot.ts:14` was already stale (24 vs 30 in prose) before this feature — bringing it to 32 in the same PR was the correct action even though the product-spec scoped the drift discharge to agent surfaces only.
**Rejected alternatives**: Keeping `register_offline_account`'s inline `MessageToDict` — lost (DRY violation; the shared helper is the canonical form going forward); client-side broker_type validation for deregister — lost (trading backend already handles it, and adding a client-side guard that disagrees with the backend invariant creates a maintenance trap).
**Scars & gotchas**: (1) **`test_tools_endpoint.py` exact-match set** (`tests/test_tools_endpoint.py:22-54`): the test asserts the EXACT set of tool names as a `names == {...}` equality; adding any new tool requires appending the name(s) to that set or the test fails. This guard is easy to miss when adding a new tool and not reading the test file. (2) **`COPILOT_MCP_TOOL_COUNT` in xstockstrat-ui**: `services/xstockstrat-ui/src/lib/copilot.ts:14` must be kept in sync with every agent-tool addition henceforth — it was already stale before this feature. No test asserts a specific value, so drift is invisible in CI. (3) **BrokerAccount descriptor-parity test**: `test_broker_account_client.py` freezes the 12-field contract of `BrokerAccount`; any future proto field added to `BrokerAccount` in `trading.proto` requires updating the parity test. (4) **Credential-safety by structure**: `BrokerAccount` proto message has no credential field — `MessageToDict` is safe. However, `UpdateBrokerAccountCredentialsRequest` does carry credentials; the agent wrapper passes the request through to the trading backend and never reflects it back in the response, which carries only `account` (no credentials). This structural guarantee must be preserved if the request or response message shapes ever change. (5) **Renumber 162→164**: this feature shipped under NNN 162, which collided with `162-fix-insights-offline-ticket` (earlier creation date). An operator-authorized renumber moved it to 164 (2026-08-31, PR #1048). The rename touched `feature dir + provenance comments in agent/CLAUDE.md, client.py, tools.py, tests/*, mcp-tools.md` — no behavior, API, schema, or migration change.
