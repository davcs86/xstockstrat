## Gotchas & scars

- **Python config getters honour a stored `0`/`""`; a key where `0` is unsafe must read through a clamp (feature 244).** In analysis, ingest and indicators, `ConfigWatcher.get_int/get_str/get_float` use `HasField` (like `get_bool` and the Node `??` getter), so a stored `0`/`0.0`/`""` is the effective value and only an absent or mismatched-type value falls back to the default. The old `*_present` names are kept as aliases. A key where `0`/`""` would break the consumer (a `Semaphore(0)`, a `sleep(0)` busy-loop, a zero pool size or range, an empty id) is read through the module-level `int_positive`/`float_positive`/`str_nonempty`, which map a stored ≤ 0 (or `""`) to the default. Each service's `tests/test_config_read_classification.py` AST guard fails when a new config read is in neither its clamp set nor its honour set, so a new key needs a deliberate classification. Evidence: `services/xstockstrat-analysis/app/config/watcher.py#get_int` (`HasField`) and `#int_positive`; `services/xstockstrat-ingest/app/config/watcher.py#int_positive`; `services/xstockstrat-indicators/app/config/watcher.py#int_positive`; `services/xstockstrat-analysis/tests/test_config_read_classification.py#FR3_KEYS`; Node `services/xstockstrat-config/src/services/configWatcher.ts#getInt`; oneof `packages/proto/config/v1/config.proto#ConfigValue`.
- **SEV-1 scar behind PLAT-8: `WatchConfig` scope silently defaulted to dev/all for the lifetime of every backend service.** All six Go/Python `WatchConfig` clients declared `environment`/`trading_mode` fields on their request but never populated them — a purely additive-looking gap that produced no error, just the wrong config scope, indefinitely. Fixed as hotfix `fix-watchconfig-clients-omit` (commits `1eaf6c8`/`1413399`/`d7d185f`, PR #891). (The `trading_mode` half of the request was later removed entirely by feature 147.) The pattern to watch for: any new field added to a `WatchConfigRequest`-builder is easy to declare-but-forget-to-populate, and nothing catches it short of reading the server-side scope a request actually resolves to.
- **ts-proto is the strict path; protobuf-es tolerated the old shape.** The whole Timestamp/enum class of bugs (PLAT-F1/F2/1/2) stayed latent for as long as the frontends called backends over Connect-HTTP (protobuf-es), which tolerates `{seconds}`/ints; it surfaced *en masse* when everything moved to the gRPC path. When touching any Node gRPC (de)serialization, assume ts-proto's stricter rules. Evidence: PR #442 message body.
- **The proto `Timeframe` enum is not interval-ordered** (`15MIN=5, 1HOUR=3, 1DAY=4, 1MIN=1, 5MIN=2`); never infer bar duration from the enum number. Only `TIMEFRAME_1DAY` is requestable — `1MIN`/`5MIN` and, since feature 143, `15MIN`/`1HOUR` are all `[deprecated=true]`. Evidence: `packages/proto/common/v1/common.proto:85-92`.
