## Swallowed / silenced errors

### D-02 Portfolio fill pipeline swallows DB errors, then emits ledger events — SEV-1 · leverage H÷S
- **Evidence:**
  - `services/xstockstrat-portfolio/internal/service/portfolio_service.go:258` — `existing, _ := s.repo.GetPosition(ctx, fill.UserID, fill.Symbol, mode, fill.AccountId)`.
  - `:303` — `_ = s.repo.ClosePosition(...)`, followed by `emitEvent("portfolio.position.closed")`.
  - `:307` — `_ = s.repo.UpsertPosition(...)`, followed by `emitEvent("portfolio.position.opened|updated")`.
- **What it hides:**
  - A transient read error looks the same as "no position". A buy then overwrites qty with `fill.Qty`, because `UpsertPosition` is absolute. A partial sell computes `newQty<0`, which routes to `ClosePosition` and deletes the whole position.
  - A failed write still emits a ledger close/open, and the stream cursor advances past the fill.
- **Benefit of fixing:** Positions and P&L can no longer silently diverge from fills (this matches bug-triage SEV-1: "Portfolio P&L calculation is wrong").
- **LOE:** S (estimate). Assumption: 3 sites in one function. Return the error so the stream consumer does not advance `lastSeq`. Add a unit test per site.
- **Trade-off:**
  - **Not fixing:** an unrecoverable fill loss on any DB blip. Offline accounts never get a broker sync to heal it.
  - **Fixing:** a fill retries on error, so the ledger-consumer loop must tolerate redelivery. It already does: the realized-delta code guards nil on redelivered sells.

### D-03 Alpaca cancel: 422 "already filled/canceled" treated as success → order marked CANCELED, fill never emitted — SEV-1 · leverage H÷S
- **Evidence:**
  - `services/xstockstrat-trading/internal/broker/alpaca.go:223-224` — `// 204 No Content is success; 422 means already filled/canceled` and `if resp.StatusCode != http.StatusNoContent && resp.StatusCode != http.StatusUnprocessableEntity { … }; return nil`.
  - `services/xstockstrat-trading/internal/service/trading.go:1256` then sets `order.Status = ORDER_STATUS_CANCELED` unconditionally.
- **What it hides:** Cancelling an order that already filled at the broker records CANCELED locally. `pollFills` skips terminal orders, so `order.filled` is never emitted, portfolio never sees the fill, and reconciliation later finds an "unexplained" position.
- **Benefit of fixing:** The local order state matches the broker on the cancel-vs-fill race.
- **LOE:** S (estimate). Assumption: surface 422 as a distinct sentinel, then re-`GetOrder` from the broker and adopt its status. Add one test.
- **Trade-off:**
  - **Not fixing:** a lost fill on every cancel/fill race. This can falsely halt the account via reconciliation.
  - **Fixing:** one extra broker GET on the 422 path only.

This is bug-triage **SEV-1** ("Orders … executing incorrectly on the live API"); route via `/sdd-triage` Track A. → signal-map: no metric distinguishes "flatten succeeded" from "flatten returned stored rejection".
