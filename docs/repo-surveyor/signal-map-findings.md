### SEV-2

### S-01 Trading: a flatten that exits early leaves an expired-protection position unpaged — SEV-2 · leverage H÷XS
- **Point:** `services/xstockstrat-trading/internal/service/trading.go:2859,2865,2873,2885` — `flattenAndHalt` returns after a `WARN` when the broker is missing, the account is offline, the entry order is not in memory, or `GetPosition` returns an error or `Qty == 0`. The only halt-and-page is `haltAccount` at `:2947`, reached only after flatten retries are exhausted. Existing signal: `WARN` only.
- **Why it matters:** the `:2884` condition `err != nil || position == nil || position.Qty == 0` merges two different states. `Qty == 0` is legitimately flat (the stop leg filled). `err != nil` is "we could not tell whether the position is open" after the protection window has expired. The early returns never call `UpdateBracketStatus` (only the success path does, `:2938`), so the bracket is likely re-selected and the same `WARN` repeats every watchdog tick.
- **Add:** counter `trading_flatten_outcome_total{outcome=no_broker|offline|no_order|flat|lookup_error|flattened|halted}` (6–7 bounded values) using the Go OTel meter in `internal/telemetry/otel.go`. Split the `:2884` branch so the `lookup_error` outcome logs at `ERROR` and raises the operator alert, while `flat` stays `INFO`.
- **Question it answers:** "did any position stay unprotected past its deadline, and was anyone told?"
- **Trade-off — without it:** an unprotected live position surfaces only as a repeating `WARN` in Loki. **With it:** one counter, no per-order label (`order_id`/`account_id` stay in logs). Cost: a portfolio-read outage will page, which is the intended behavior for an expired window.
- Behavioral fix (halt vs return) belongs to debt-radar; this finding is the signal half (RS-N5).

### S-02 Trading: a bracket lookup failure returns with no row, no alert and no watchdog coverage — SEV-2 · leverage H÷XS

- **Trade-off — without it:** no `order_brackets` row means the protection watchdog has nothing to scan, so the entry is unprotected and silent. **With it:** a page during a DB blip; accept, since the alternative is silence on a live-money path.

### S-04 Cross-service: background loops have no liveness signal — SEV-2 · leverage H÷S
- **Point:** a hang or silent stall inside a tick stops fills, reconciliation, ingestion or polling with nothing to alert on. A panic is loud (process exit); a wedged call is not. Verified sites:
  - **trading** — six pollers started at `cmd/server/main.go:117-127` (fill `trading.go:1732-1738`, reconciliation `:1927-1933`, position sync `:2344-2353`, credential health, bracket watchdog, order-intent sweeper `order_intent.go:114-120`). Only position sync has a cycle line (`:2360`) and a stall watchdog.
  - **marketdata** — five `go svc.Start…` pollers at `cmd/server/main.go:160-168`; the warm poller logs failures only (`marketdata_service.go:1146-1179`).
  - **ingest** — the mcp_client loop task reference is dropped with no done-callback (`app/main.py:127`; compare `config/watcher.py:72`).
  - **analysis** — the four supervised `*_forever` loops log only on *exit* (`app/supervision.py:23-37`); `live_loop` is covered by S-08.
  - **portfolio** — five ledger consumers in `consumeEventStream` (`portfolio_service.go:190-208`), see S-05.
- **Add:** one observable gauge per service, `<service>_loop_last_success_timestamp_seconds{loop}`, set at the end of each successful tick (`loop` = a fixed name, ≤ 6 per service). Alert shape: `time() - gauge > 3 × interval`. Cheapest type that answers the question: a timestamp, not a histogram.
- **Question:** "is each safety and ingestion loop still ticking?"
- **Trade-off — without it:** a wedged loop is indistinguishable from an idle one (the platform doc already notes a missing series reads as "no traffic"). **With it:** ≈ 20 series in total (estimate), one instrument per service. A new series must be added to `produced-signals.tsv` before an alert can use it (`scripts/check-otel-produced-signals.sh`).

- **Trade-off — without it:** a deterministic handler error blocks every later fill for every user, and a park is a one-line `ERROR`. **With it:** ~25 bounded series. Cross-ref debt-radar D-47.

### S-07 Marketdata: the feed giving up is an `ERROR` line, and the documented alert path is unreachable — SEV-2 · leverage H÷S

### S-08 Analysis: the registered liveness literal is logged even when every pair errored — SEV-2 · leverage H÷S
- **Point:** `app/engine/live_loop.py:343-345` logs `live_loop: cycle complete` after `_run_cycle()` returns. Per-pair exceptions are caught inside (`:470-479`) and only counted in a log line (`:481`), and the zero-live-strategy early return (`:436-437`) also falls through to the literal. The liveness alert therefore cannot tell a healthy loop from a 100% failing one.
- **Also:** the owner drains return a *partial* set after a `WARN` (`:556-567`) — a held position that drops out has its exit rule skipped that cycle. `GetBars` is called with no deadline (`:702`) and no `timeout` appears anywhere in the file, so a hung call freezes the loop. The "previous cycle still running" branch (`:339-341`) is dead code: the same coroutine holds the lock while it awaits the cycle. Alert triggers and throttle suppression leave no signal (`:838-850`).
- **Add:**
  - counters `analysis_live_loop_pairs_total{outcome=evaluated|error|no_bars}` and `analysis_live_loop_drain_failures_total{source=held|watchlist|signals}`;
  - `analysis_live_loop_triggers_total{trigger=entry|exit, outcome=alerted|throttled|alert_failed}`;
  - a cycle-duration histogram (no labels) and a per-cycle `asyncio.timeout` with an `ERROR`.
  - **Keep the `:345` literal and its text unchanged** — an alert depends on it (`produced-signals.tsv:23`); do not gate it on errors.
- **Question:** "what is the live-evaluation success ratio, and are we skipping exits because of an upstream outage?"
- **Trade-off — without it:** a live strategy can be silently blind. **With it:** four bounded counters; `strategy_id`/`symbol` stay out of labels (H-03).

### S-09 Agent: auth rejects and OAuth failures are uncounted, and an mTLS fault is reported as a 401 — SEV-2 · leverage H÷S
- **Point:**
  - `app/main.py:157-164,223-225` and `app/auth.py:83-84` — a missing token or an audience mismatch is a silent 401.
  - `app/auth.py:97-99` — any non-gRPC exception returns `None` (a 401). `mtls.secure_channel` is built inside that `try` and raises `RuntimeError` when `MTLS_*` is unset (`app/mtls.py:20-23`), so a certificate fault looks like "every token is invalid". It is logged at `error`, uncounted, and has the wrong status (the 503 path at `main.py:201-227` exists for exactly this).
  - `app/oauth_server.py:259-269` — token exchange and refresh failures return `invalid_grant` with no log; `:170-171` returns `invalid_client`; `:202-204` returns `bad txn`. An identity outage looks like a client mistake.
- **Add:**
  - counter `mcp_auth_rejected_total{reason=missing|invalid|aud_mismatch|identity_unavailable|internal_error}`;
  - counter `oauth_requests_total{grant_type, outcome=ok|invalid_grant|server_error}` and `oauth_txn_rejected_total{reason=bad_sig|state_mismatch|malformed}`;
  - a `warning` log at the swallow points carrying the gRPC code or exception class, never the code, token or state.
- **Question:** "is a client misconfigured, is identity down, or is the agent's own mTLS broken — and are connectors failing to refresh?"
- **Trade-off — without it:** a certificate expiry would force every MCP client to re-authenticate with one `error` line as the only trace. **With it:** ~15 bounded series. Moving `internal_error` to a 503 is a status-mapping change (debt-radar lens).

### S-10 Identity: login, token-validate, code-exchange and refresh rejects are all the same code 16 — SEV-2 · leverage H÷S
- **Point:** `services/xstockstrat-identity/src/grpc/identityServiceImpl.ts:143-144` (unknown or inactive user) and `:159-162` (bad password) both return `invalid credentials`; the seed-admin refusal (`:152-155`) logs a `WARN` but is returned the same way. `:202-204` — `validateToken` turns *every* error into code 16 with no log, including a missing `JWT_SECRET` (the getter throws inside the `try`). - **Trade-off — without it:** a brute-force attempt or a secret rotation break is invisible beyond a status-16 count. **With it:** ~12 bounded series; `user_id`, `email`, `client_id` stay in logs (H-03). See NC-2 and NC-3 before relying on the "status 16 exists" assumption or on lockout.

## Redundant / noisy signals  (remove or demote — noise cut is half the job)

### N-01 Ingest: a per-item `INFO` on every dedup hit, and raw third-party items in warnings — SEV-3 · leverage M÷XS
- **Signal:** `app/handlers/servicer.py:1161-1167` logs one `INFO` per deduplicated signal. Dedup hits are the *steady state* for polled sources (each cycle re-delivers current signals every `poll_interval_seconds`, default 300), so volume scales with sources × items × cycles. `app/extractors/mcp_client.py:34,38` log the full raw item (`%r`) with no source slug.
- **Remove/replace:** replace the dedup line with the `ingest_signal_outcome_total{outcome=deduplicated}` counter from S-15 and keep a `debug` log; log a truncated item plus the slug, or one aggregate per cycle.
- **Trade-off — removing:** noise and Loki cost cut vs. losing per-signal dedup visibility (still available at `debug`). Neither literal is in `produced-signals.tsv`; Grafana-side alerts are unknown (NC-8).

### N-02 Fixed-interval retries with no backoff flood logs during an outage — SEV-3 · leverage M÷XS
- **Signal:** ledger `eventNotifier.ts:130-137` (fixed 2 s, a `warn` per failed connect, `:120`); indicators `app/config/watcher.py:90-92` (fixed 2 s `warn`); portfolio `portfolio_service.go:196-206` (`time.Sleep(2s)` per consumer, five consumers, `ERROR` each time).
- **Replace:** exponential backoff with a cap (config already does 1 s → 30 s, per its `CLAUDE.md`), log the first failure and the recovery, demote graceful GOAWAY reconnects (`:201`) to `debug` or a counter.
- **Trade-off — removing:** noise cut vs. slower reconnect after a short blip (bounded by the cap).

### N-03 Portfolio: a bare `slog.Warn` per position on the read hot path — SEV-3 · leverage M÷XS
- **Signal:** `portfolio_service.go:484` `slog.Warn("latest quote has no usable price", "symbol", ...)` runs inside the `applyQuotes` loop on `GetPortfolio`/`ListPositions`, which the UI polls. It also uses `slog.Warn` rather than `WarnContext`, so it carries no `trace_id`.
- **Replace:** one aggregated log per call with a count and a bounded sample, or the S-06 counter.
- **Trade-off — removing:** per-symbol detail in Loki vs. flood during a quote outage; the sample keeps diagnosability.

### N-04 Trading: systemic escalation re-fires every tick while the threshold holds — SEV-3 · leverage M÷XS
- **Signal:** `trading.go:2205-2246` — `escalateSystemic` is called on each reconciliation tick while ≥ the threshold of accounts error, re-issuing `SetConfig(REDUCE_ONLY)` and a CRITICAL page every 60 s; unlike the per-account path (`isAccountHalted`, `:1974`) there is no "already REDUCE_ONLY" check.
- **Replace:** skip when the state is already `REDUCE_ONLY`/`HALTED`, and count suppressions (`trading_alert_emit_total{category=reconciliation, outcome=suppressed}`).
- **Trade-off — removing:** alert-fatigue and config churn cut vs. a re-page if the first alert was lost (S-03's `outcome` counter covers that).

### N-05 Indicators: a per-call `INFO` in the formula hot path with no diagnostic value — SEV-3 · leverage M÷XS

- **Replace:** drop it and log only on non-success (S-21).
- **Trade-off — removing:** volume cut at no visibility loss. Not in `produced-signals.tsv`.

### N-06 Analysis: per-component and per-symbol `INFO` inside evaluation loops — SEV-3 · leverage M÷XS

## Cardinality / cost hazards

### H-01 Wrapping the FMP HTTP client with `otelhttp` would put the vendor key into traces — SEV-2 (if implemented naively)
- **Hazard:** `services/xstockstrat-marketdata/internal/fmp/fmp_client.go:239` builds the URL with `params.Set("apikey", c.apiKey)`. `otelhttp` records the full URL, query string included, as a span attribute, so the key would land in Tempo. The code already redacts the URL from errors (`:280,289`), which shows the intent.
- **Safer form:** instrument the four vendor chokepoints manually (S-12), or wrap only the Alpaca client (header auth). If a transport wrapper is used, strip the query before it is recorded.

### H-02 New dimensions multiply histogram buckets, and a client gRPC handler brings unbounded siblings — SEV-3
- **Hazard:** adding `rpc.method` to the BFF histogram (`bffMetrics.ts`) multiplies every series by the bucket count; adding `otelgrpc.NewClientHandler()` in the Go services would create `rpc.client.*` size/count instruments that the drop views do not cover (`services/xstockstrat-portfolio/internal/telemetry/otel.go:84-100` drops only the four `rpc.server.*` siblings; the other Go services were not re-read).
- **Safer form:** a separate bucket-free counter for per-method outcome (M-03); extend the drop views in the same change as any client handler.

### H-03 Dimensions to keep out of every proposed metric label — SEV-3
- **Hazard:** each proposed counter above is safe only on fixed enums. Keep these in logs or span attributes: `user_id`, `email`, `client_id` (open dynamic registration mints one per client), `account_id`, `order_id`, `intent_id`, `symbol` (the warm set is demand-driven and unbounded), `strategy_id`, `stream_key`, `subId`/`clientId`, signal-source `slug` (owner-chosen free text), notify `category`/`sourceService` (request-supplied), GetSecret `key` and the `x-internal-caller` header value.
- **Existing series are fine:** `mcp.tool.duration` clamps the tool label to the registered set (`tool_metrics.py:51`); `http.server.duration` uses a static route template; the RPC histogram labels are bounded.
- **Do not rename:** `rpc.server.duration`, `mcp.tool.duration`, `http.server.duration` and their attribute keys, or the `live_loop: cycle complete` literal — alerts query them (`produced-signals.tsv`).
